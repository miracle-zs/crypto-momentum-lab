## 确认的缺陷

### R2-01 / P1：固定金额选优丢弃了权益曲线不可行标记

位置：`generate_six_scenarios_dashboard.py:897`，以及 `select_pnl_max`、`select_balanced` 对返回值的接受逻辑。

`evaluate_equity_curve` 在期间权益不大于零时已经返回 `is_feasible=False`，但 worker 没有检查该标记，仍返回盈利指标。固定金额 selector 只要求最终 PnL/Calmar 为正，可以推荐中途权益已跌至负数的参数。

实际反例：11 个标的各开 100U 名义仓位，保证金合计 220U，价格从 100 跌至 1、随后在 110 平仓。最低账户权益 **-89.77U**，指标层明确不可行，验证器却返回 **+108.38U**，`select_pnl_max` 确实接受。280U 保证金上限并不能替代账户可行性检查。

建议：在验证器统一拒绝 `not metrics.is_feasible`，保留原因并让所有目标函数共享此门槛。不要把“完整路径不可行”压缩为仍可排名的有限风险数值。此建议沿用模块现有的权益可行性定义，不涉及新建交易所强平模型。

### R2-02 / P1：看板重放再次扩大了已验证的研究窗口

位置：`generate_six_scenarios_dashboard.py:650`、`:661`、`:2783`、`:2797`。

验证器已使用 manifest 窗口，但看板调用 `get_scenario_events` 时重新从事件推导窗口；随后以所有曲线的最早入场、最晚退出决定 `common_start/common_end`，没有使用同一个 manifest 截止时间。窗口外平仓又进入展示指标和曲线，首尾无交易区间也被丢弃。

完整寻优到看板反例：研究截止 **00:05**，一笔已在 00:03 平仓、另一笔 00:04 入场并于 00:10 退出。寻优选择结果 PnL **9.78U**，同次调用返回的看板 PnL **19.71U**，曲线实际结束于 **00:10**。

建议：展示直接使用已验证结果的成交与窗口；如需要重算曲线，必须复用相同上下文和 manifest 起止，基线也使用同一窗口。不能再以未来退出时间决定研究结束时间。

### R2-03 / P1：看板定时平仓仍缺少价格流

位置：`generate_six_scenarios_dashboard.py:632`、`:674`、`:2762`。

`get_scenario_events` 不接收价格流，调用账本时也未传 `price_series`。只要触发定时强平，账本仍回退为入场价，并把错误退出价写入成交。后续 `to_trade_records` 即使收到价格流，也不会重新纠正已记录的退出价格。前一轮只修到了粗筛和 worker 路径。

反例：100 入场、强平时行情为 105，已修复验证器得到 **+4.86U**；看板成交仍以 **100** 平仓，净收益 **-0.14U**。

建议：优先取消展示侧重复决策；若保留，显式传入同一价格流和风控配置，并增加“selector 指标 = 同上下文展示指标”的集成断言。

### R2-04 / P1：非 1000U 起始权益产生虚假窗口回撤

位置：`simulation_ledger.py:692`。

净值重建正确使用 `state_in.total_equity_mtm`，但紧接着 `evaluate_equity_curve(pts)` 忘记传该基准，落回默认 1000U。滚动账户亏损后进入下一窗口，或显式使用不同初始资金，都会产生不属于当前窗口的回撤。该接口没有保存历史高水位，因此固定 1000U 也不能解释为合法的账户全历史高水位。

反例：当前窗口从 **900U** 开始，一笔平价交易只损失 **0.14U**。账本报告 MDD **100.14U**，同一组净值点使用正确初始权益重算得到 **0.14U**。

建议：把窗口起始权益传给指标函数；如果产品需要全历史回撤，应在 PortfolioState 中显式携带高水位，单独定义该指标，不能用常量替代。

### R2-05 / P2：全部交易未平仓时看板崩溃

位置：`generate_six_scenarios_dashboard.py:2785`。

`all_trades_flat` 非空只说明有交易，不说明有已平仓交易。当前 `max(t.exit_time for ... if t.exit_time is not None)` 在全未平仓时计算空集合。

实际调用 `compute_six_scenarios_view`，输入一笔有效但尚未平仓的机会，得到 **ValueError: max() iterable argument is empty**。这是一种有效的窗口末状态，不应让整份报告失败。

建议：直接以研究窗口结束时间为估值截止；没有平仓也应展示持仓 MTM。与 R2-02 使用统一窗口可以一起解决，但应保留单独的全未平仓回归案例。

## 架构改进：统一评估上下文与结果的传递

当前最重要的问题不是文件长度，而是同一参数在三个入口中重新解释：寻优 worker、看板重放、WFA 账本。价格、窗口、可行性和初始权益在这些调用间丢失。本轮五个反例都是这种信息传递不完整的具体后果。

建议收敛到一个模块接口：

```text
evaluate_candidate(context, candidate, scenario, include_curve=False)
    -> EvaluationResult
```

- `context` 包含快照、有序机会池、价格、起止时间、起始状态和成本。
- `scenario` 显式表达资金规模规则、保证金约束、定时风控和目标函数。
- `EvaluationResult` 包含窗口、可行性及原因、指标、实际成交，以及可选净值数组。
- selector 只排序已验证结果；看板只展示结果；多进程适配器只分发相同上下文的计算。

这会把规则和验证集中到一个位置。各目标函数仍可不同，不应强行把收益最大、稳健比和复利收益合成同一个目标。

实施顺序：先让现有 worker 返回足够的结果并让看板复用，再迁移 WFA。无需一次重写整个账本；先用结果一致性案例锁定每次迁移的行为。

## 性能采样与优化顺序

合成负载结果（带 profiler，单机单次采样）：

| 路径 | 5 次调用累计耗时 | 解释 |
|---|---:|---|
| `_verify_single_contender` | 约 0.744 秒 | 精算入口总耗时 |
| `reconstruct_mtm_equity` | 约 0.624 秒 | 约占入口耗时 84% |
| `_eval_current_mtm` | 约 0.351 秒 | 包含在重建耗时内，不能相加 |
| `get_price_at` | 约 0.127 秒，300,000 次 | 包含于逐持仓估值中 |
| `evaluate_equity_curve` | 约 0.058 秒 | 风险指标 |
| `simulate_window` | 约 0.038 秒 | 本负载中的成交准入 |

五次精算生成 57,605 个采样点，累计约 218 万次函数调用。这里测的是重复精算内核，不使用结果缓存，数字不能直接外推到全量网格、复利模式或真实数据耗时。

优先优化：

1. **复用时间轴和报价索引。** 在不可变上下文中，为每个标的预对齐到共同 15 秒时间轴，保持只使用当时及之前报价的规则。候选之间复用对齐结果，减少重复二分。退出等事件时刻仍需保持原有精确处理。
2. **精算保留数值数组，最终展示再装配对象。** 评估阶段不必为每个点建立 datetime/EquityPoint 并逐字段 round。保留权益/保证金等数组足以算风险；只有最终入选曲线需要完整展示对象。CDaR 等指标需要保留适当数组，不能简单假定所有统计都可无损流式计算。
3. **在同一上下文内复用成交准入结果。** 固定金额和复利估值可能共享基础成交集合；只有规则完全一致时才复用。缓存必须受快照、窗口、风控和资金规则约束，不能只凭参数相同合并。
4. **再测粗筛和多进程内存。** 当前粗筛主循环仍串行，spawn 给各进程传整套 Python 对象。下一步应使用固定真实快照分别记录粗筛、精算、序列化、总 RSS，再决定参数块并行或共享只读 NumPy/memmap。当前证据不足以声称增加 worker 一定加速。
5. **保留 Pareto 改进为次优先级。** 通用 Pareto 仍有 O(N²) 扫描，但本次精算内核采样没有证明它是主瓶颈。先量化真实可行候选集规模，避免把时间花在非热点上。

前一轮建议的复利高水位增量计算已经落实，不再把该项列作未完成优化。

## 修复与验收优先级

先修 R2-01 的可行性传播；然后一起修 R2-02/03/05 的展示上下文，再修 R2-04 的权益基准。验收应覆盖完整“选优结果→看板”一致性，不能只测 worker helper。性能优化在这些语义锁定后进行，比较数组输出与参考实现，并测固定真实快照的耗时和内存。

本轮没有对所有模块作形式化证明，也不把 190 项通过解释为没有其他缺陷。报告只把已实际执行反例的五项列为确认缺陷。
