# 机会池完整性与 Walk-forward 连续评价修复设计

日期：2026-09-21。状态：设计方案，尚未实现；本文件只定义数据、回放和评价口径，不修改交易代码或服务器配置。

## 1. 目标与结论

本地参数寻优需要回答两个独立问题：

1. 这组参数在所有可能的交易机会中会怎样表现；
2. 在某个历史时点冻结这组参数后，它在之后从未参与选优的数据上会怎样表现。

当前 `account_primary_events.csv`、`account_acc02_events.csv` 更接近“某组参数和某个账户已经触发或成交的事件”，已经经过当前策略、持仓槽位和保证金限制过滤。它们不能代表完整的参数寻优机会池。当前 Walk-forward 只加载两份账户事件，并且会丢弃跨窗口持仓，因此训练、验证和 OOS 的边界不连续。

修复后的原则是：

- 用参数无关的原始机会池承载“当时所有可评估机会”；
- 用统一的逐时刻执行账本模拟不同参数；
- 用 `state_in` 和 `state_out` 连接相邻 Walk-forward 窗口；
- 用窗口两端的 MTM 总权益差计算 OOS，而不是用累计已实现收益相减；
- 将服务器实际成交作为独立证据流，用于对照模拟结果，不让实际成交集合替代原始机会池。

## 2. 当前问题及影响

### 2.1 机会池已经受当前参数污染

现有 [run_walk_forward_analysis.py](../../../local_optimization/run_walk_forward_analysis.py) 的 `load_all_replay_events` 只读取两份账户事件文件。这些文件中的机会已经经历了当时的信号参数、账户身份、持仓数量和资金限制。没有被当前配置触发的信号不会出现在文件中，候选参数只能在既有成交集合上重新筛选。

如果寻优参数会改变信号检测逻辑，例如窗口长度、动量阈值或突破阈值，固定的当前成交集合无法覆盖整个搜索空间。即使参数只改变入场过滤，也必须确认原始池是搜索范围的超集。

### 2.2 跨窗口持仓被同时丢弃

当前窗口过滤逻辑会要求入场和退出都落在同一个窗口内。这样会漏掉：

- 训练窗口内开仓、OOS 窗口内平仓的持仓；
- OOS 开始前已持仓、OOS 内继续持有的仓位；
- OOS 结束时仍未平仓的仓位。

结果会低估持仓延续期间的浮亏、保证金占用和恢复时间，也会把真实退出收益分配到错误的日期。

### 2.3 日报 OOS 不是冻结前向评价

当前日报主要用累计 `net_pnl` 的差值比较旧参数和新参数，没有完整保存参数冻结时点、期初组合状态、机会池版本、价格版本和 OOS 边界。因此它不能严格证明“当时已经选定的参数，在后来新增的一段数据上表现如何”。

## 3. 领域对象与数据边界

### 3.1 原始机会 `RawOpportunity`

每一条候选机会必须有稳定的 `opportunity_id`。机会记录至少包含：

| 字段 | 含义 |
|---|---|
| `opportunity_id` | 全局唯一、跨账户和跨参数稳定的 ID |
| `symbol`、方向 | 标的和多空方向 |
| `detected_at` | 信号被检测到且可用于决策的时间 |
| `entry_eligible_at` | 最早可以执行入场的时间 |
| `entry_reference_price` | 回放使用的可得价格或价格区间 |
| `exit_rule` / `exit_reference` | 退出条件、参考价格或退出事件 |
| 特征快照 | 参数过滤所需的特征值及其生成时间 |
| 成本字段 | 手续费、滑点、资金费所需的信息 |
| `strategy_version` | 产生机会的策略代码/特征版本 |
| `market_data_version` | 产生机会时使用的行情版本 |
| `status` | 见下方状态机 |

机会状态应至少区分 `DETECTED`、`FILTERED`、`ENTRY_REJECTED`、`ENTERED`、`EXITED`、`EXPIRED` 和 `CARRY_IN`。被参数过滤或被保证金拒绝的机会也要保留，这样才能解释“为什么没有成交”，并和服务器实际结果对照。

### 3.2 模拟执行与实际执行分离

- `SimulationExecution`：由本地回放器根据某组参数生成的订单、成交和持仓批次。
- `ActualExecution`：服务器真实的信号、订单、成交、拒单、撤单和账户状态。
- `PortfolioState`：某个账户、某组参数在一个确定时刻的现金、持仓、未实现盈亏、总权益、保证金和风险状态。

实际执行可以用于验证模拟，但不能用来构造模拟机会池。否则当前服务器参数会把未触发的机会提前删掉。

### 3.3 数据快照 `DataSnapshot`

每次本地导入生成不可变的快照身份，至少记录：

- `snapshot_id`；
- 目标截止时间和实际各数据流 watermark；
- 机会池、行情、成交和账户状态的版本或内容哈希；
- 币种覆盖、时间覆盖和缺口；
- schema 版本、时区和导入批次。

数据流不能只通过“文件存在且有内容”判断完整。任何关键流没有覆盖截止时间、存在时间缺口、重复 ID 或关键字段不可解析，都应阻止正式寻优。

## 4. 完整机会池方案

### 4.1 数据来源选择

需要采用以下两种方式之一：

1. **服务器导出参数无关的原始机会池**：服务器每天导出所有信号检测结果、过滤上下文和可执行价格；
2. **本地使用完整行情重放检测逻辑**：本地从 15 秒行情、特征和历史状态重新生成机会。

如果服务器目前只能导出 `account_*_events.csv`，在新增原始机会导出或本地信号重放之前，报告必须标记为“代理机会池分析”，不能标记为完整参数空间寻优。

### 4.2 覆盖搜索范围

机会池必须覆盖全部待搜索参数可能产生的机会：

- 参数只影响后续过滤时，可以生成覆盖搜索范围的机会超集，然后在本地应用过滤；
- 参数会改变检测逻辑时，必须按候选参数重新检测，或导出足够的原始特征让本地检测能够重建信号；
- 不能用当前线上参数已经成交的集合推断其他参数的机会集合。

### 4.3 导出包和完整性校验

每天服务器导出包建议包含：

```text
manifest.json
opportunities.parquet
market_data / mark_prices
actual_signals.parquet
actual_orders.parquet
actual_fills.parquet
portfolio_snapshots.parquet
fees_and_funding.parquet
```

`manifest.json` 记录截止时间、来源版本、文件哈希、行数、时间范围、币种范围、账户范围和缺口。导入时执行以下校验：

- `opportunity_id` 唯一且可追踪；
- 事件按可用时间排序，重复和倒序明确处理；
- 所有关键时间带时区并可转换为 UTC；
- 行情和机会覆盖所有需要的币种及窗口；
- 所有费用、资金费和外部现金流都有来源；
- 最近重叠区间可以修订晚到数据，但旧运行不被覆盖，而是生成新的 snapshot revision。

## 5. 统一逐时刻回放账本

所有参数候选必须走同一个回放器，不能在候选表有 `full_net_pnl_usdt` 时直接把汇总值当作复利结果。每个时间点的处理顺序固定为：

1. 读取当时已经可用的机会和价格；
2. 应用候选参数过滤；
3. 按预先固定的顺序检查持仓槽位、保证金、冷却和账户限制；
4. 生成模拟订单和成交；
5. 更新持仓批次、现金、手续费、资金费和未实现盈亏；
6. 记录总权益、保证金、峰值权益和回撤；
7. 处理退出、过期和窗口边界状态。

同一个机会在同一组参数下只能生成一次进入决策。事件排序要固定处理同一时间戳下的价格、退出、入场和资金费，避免并行完成顺序改变结果。

统一账本应同时服务于：

- 历史全窗口回测；
- 六场景约束筛选；
- Walk-forward 训练、验证和 OOS；
- 动态复利仓位；
- 实际成交对照。

## 6. Walk-forward 窗口设计

### 6.1 窗口结构

每个 fold 使用半开区间：

```text
训练集：     [train_start, train_end)
验证集：     [valid_start, valid_end)
样本外 OOS： [oos_start, oos_end)
```

训练集用于搜索，验证集用于固定候选或选择稳定参数，OOS 只接受已经冻结的参数。OOS 数据不能参与参数排序、阈值调整、候选过滤或权重调整。

日常运行流程是：

1. 以早上 8 点作为固定决策截止时间，冻结 `snapshot_id`；
2. 使用截止时间以前的训练和验证数据寻找候选；
3. 保存参数哈希和协议版本；
4. 在随后的新增区间运行冻结参数；
5. 记录 OOS 的输入状态、输出状态和指标；
6. 下一次运行时再把已结束的 OOS 数据纳入历史。

### 6.2 `state_in` 和 `state_out`

每个窗口都必须显式保存：

- `state_in`：现金、总权益、未平仓批次、开仓均价、已实现盈亏基线、保证金、冷却和风险状态；
- `state_out`：窗口结束时相同字段及未平仓批次；
- 两个状态的内容哈希和生成时刻。

下一个窗口使用前一个窗口的 `state_out` 作为 `state_in`。状态属于“账户 + 参数版本 + 时间点”，不同候选参数不能共享一个已经被其他候选改变过的持仓状态。

### 6.3 跨窗口持仓规则

例如一笔仓位在 07:55 开仓，10:00 平仓，而 OOS 从 08:00 开始：

- 08:00 加载为 `carry_in`，不能重新开仓；
- 用 08:00 的标记价计算窗口初始 MTM 权益；
- 只计算 08:00 到 10:00 的盈亏；
- 10:00 的退出属于 OOS；
- 07:55 到 08:00 的盈亏不计入 OOS，也不能在下一个窗口重复计入。

窗口结束时不强制平仓。未平仓仓位通过 `state_out` 传递到下一个窗口。最终报告可以额外提供强制平仓版本，但必须和正常连续评价分开命名。

### 6.4 研究型和生产型 WFA

建议保留两种明确模式：

- **Stateful WFA**：每个候选从其自身状态连续滚动，模拟真实上线后每天更新参数的过程；
- **Independent Fold WFA**：每个 fold 使用固定研究本金和明确的初始状态，用于比较参数在同一条件下的可比性。

两者不能混成一张榜单。日报用于判断实际参数是否应更换时，以 Stateful WFA 为主，同时保留 Independent Fold 作为研究诊断。

## 7. OOS 指标口径

每个 OOS 窗口至少保存：

- 起点和终点 MTM 总权益；
- `oos_pnl = equity_mtm_end - equity_mtm_start`；
- 按固定时间网格计算的收益、MDD、Ulcer Index 和 CDaR；
- 日内最大回撤、最长水下时间和恢复时间；
- 峰值保证金、平均保证金、拒单数和成交数；
- 手续费、资金费、滑点和外部现金流；
- 期初/期末未平仓数量及 carry-in/carry-out 数量。

不能把所有收益归到平仓日，也不能通过删除期末未实现亏损来提高 OOS 分数。OOS 结果必须关联 `parameter_hash`、`snapshot_id`、`pool_version`、`price_version` 和 `state_in_hash`。

## 8. 对现有代码的改造映射

### 8.1 机会池加载

将 [run_walk_forward_analysis.py](../../../local_optimization/run_walk_forward_analysis.py) 中只读取两份账户事件的逻辑替换为统一机会池加载器，支持：

- manifest 和 watermark 校验；
- 全账户、全币种和全时间范围读取；
- 稳定 ID 去重；
- 原始机会和实际成交分离；
- 数据不足时阻止正式寻优。

### 8.2 窗口过滤

将当前按“入场和退出都必须位于同一窗口”的过滤逻辑替换为带 `state_in` 的连续回放。窗口过滤只负责提供时间边界，持仓生命周期由回放账本管理。

### 8.3 六场景寻优

移除 [generate_six_scenarios_dashboard.py](../../../local_optimization/generate_six_scenarios_dashboard.py) 中使用网格汇总字段代替真实回放的正式选优分支。网格汇总只能作为预筛选或诊断，不能生成最终的复利分数、回撤和持仓槽位结果。

### 8.4 日报 OOS

将 [run_daily_local_optimization.py](../../../local_optimization/run_daily_local_optimization.py) 中累计已实现收益相减的 OOS 逻辑改为固定窗口的 MTM 权益差，并保存参数冻结时点、数据版本、初始状态和输出状态。

## 9. 验收标准

实现后至少应有以下自动化验证：

1. 空机会池不能通过网格汇总值生成候选结果；
2. 同一 `opportunity_id` 在同一参数回放中不能重复成交；
3. 一笔跨窗口持仓只能被计算一次；
4. carry-in 初始权益只包含窗口开始时的权益，不重复计算窗口开始前的浮盈；
5. 训练、验证和 OOS 的数据集合严格不重叠；
6. OOS 参数哈希在窗口内保持不变；
7. 连续完整回放与分窗口 carry-in 回放的权益曲线在误差容忍范围内一致；
8. 机会池存在缺口、重复 ID 或 watermark 不足时，正式寻优被阻止；
9. 实际成交只能通过稳定 ID、时间、方向、账户和数量等字段进行逐笔对照；
10. Stateful WFA 和 Independent Fold WFA 以不同模式输出，不能混排。

## 10. 实施顺序与门禁

建议按以下顺序实施：

1. 先建立机会池 manifest、稳定 ID、时间水位和完整性门禁；
2. 再让所有候选经过同一个逐时刻回放账本；
3. 接入 `state_in/state_out` 和跨窗口 carry-in；
4. 将 OOS 改成 MTM 边界权益差；
5. 增加连续回放与分窗口回放一致性测试；
6. 最后接入日报稳定性、横向限制条件对比和实盘逐笔验证。

在第 1 至第 4 步完成前，报告应使用“代理机会池”“近似网格结果”或“非严格 OOS”等明确标签，不能把结果标记为完整参数空间寻优或可自动换参依据。
