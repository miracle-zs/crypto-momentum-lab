# 本地寻优实现审查报告

审查日期：2026-09-19。对象：`local_optimization/` 当前工作区实现及它依赖的四个 `scripts/` 未提交修改。

## 结论

**当前版本是具备部分指标函数、旧结果筛选和展示能力的研究原型，尚不能作为可信的每日参数寻优与实盘校验系统。** 不建议根据当前页面的“稳健推荐”“前向收益”“审计通过”直接决定实盘换参。

主要原因不是界面或代码风格，而是事实链尚未打通：无数据时会生成示例盈利候选；正式选优使用最大回撤的固定倍数代替 UI/CDaR；风险协议没有完整执行；样本内冠军被当成实盘配置及前向表现；权益重建丢掉未平仓和期初持仓；对账和看板存在无证据的成功结论。

可以保留的基础包括：模块初步拆分、权益/候选数据结构、UI 基础公式、Pareto 支配关系、SQLite 索引雏形、邻域搜索思路和现有测试。应先修复数据与计算闭环，再谈扩展网格或加速；不需要从头重写所有文件。

## Standards：工程与规范轴

**建议**：删除凭证明文、改成 SSH key/受控凭证引用，并保留主机校验；若该凭证有效或曾外发，轮换它。不能把 `.gitignore` 当作凭证保护措施。本次只记录问题，不擅自修改凭证或登录服务器。

### E2 · P2 · 代码、依赖和测试没有形成可复现的本地交付

**位置**：`.gitignore:20`；`pyproject.toml` 的 dependencies、pytest testpaths、wheel packages；`equity.py:19`、`run_two_stage_grid_optimization.py:23`。

**建议**：跟踪研究源码、测试和模板，仅忽略原始数据、结果、缓存及 SQLite；建立本地研究依赖 extra 或独立锁定环境，显式接入本地测试。服务器部署仍可排除本地研究模块及其依赖，不必给服务器增加运算任务。

### E3 · P2 · 核心规则重复实现，造成行为分叉

**位置**：`optimizer.py` 与 `run_two_stage_grid_optimization.py`；`reconciliation.py` 与 `run_live_reconciliation.py`；`build_opt_groups.py` 与 `dashboard.py`。

这是 **Duplicated Code / Divergent Change 的维护性判断**，不是工具可自动判定的风格违规：两套邻域用不同收益保留比例，两套选优顺序不同；CLI 对账没有复用另一套 matcher；前端同时可读产物、现场重算和回退固定值。改一个规则时难以保证各入口一致。

**建议**：只保留一个候选评估/约束/推荐模块和一个对账模块；CLI 只负责输入输出，看板只消费有版本的结果。不要为此添加更多只转发调用的类。

### E4 · P2 · 交付手册描述了不存在或不同的能力

**位置**：`HANDOVER_MANUAL.md` 第 2.3、3、4、6、8 节；`run_daily_local_optimization.py:270` 起的 argparse；`mtm_engine.py:28`。

手册把真实七维订单流参数写成 TopN、ROC、ATR 止盈等另一套含义，并声称支持相位参数、历史配置锁定和完整压力验证。实际 daily CLI 没有 `--account-id`、`--phase-offset-minutes`、`--top-n-pareto`、`--delta-tolerance`、`--out-dir`、`--data-manifest`；MTM 引擎只重建给定交易，未执行 ATR/退出状态机。两阶段程序是读取已有全网格表再筛选，不是手册描述的粗网格回测后细网格重跑。

**建议**：按实际入口重新生成用法和能力清单，把未实现内容列为计划；删除“Production Handover Ready”“100% 同构”“完整压力测试”等缺少证据的结论。收益差的代数分解也不应直接称为“正交分量”或“纯 Alpha”。

工程轴计 4 项；最高优先级为 E1 的明文凭证。工具检查失败单列在验证章节，不重复列为人工风格发现。

## Spec：设计符合性与行为正确性轴

### S1 · P1 · 缺少候选数据仍生成成功盈利结果

**位置**：`run_daily_local_optimization.py:181–205`；`dashboard.py:459–579`。

daily 入口在找不到候选 CSV 或所有行解析失败时，生成固定的 `84.50U` 收益、52 笔交易、可行候选。看板找不到优化文件或读取失败时，也能返回固定的 `356.39U` 冠军等结果。生产入口没有将这些数据隔离为显式 demo。

**复现**：对空临时目录调用 `load_candidate_evaluations`，返回 `[(84.5, True)]`。缺少输入因此可以变成成功报告。

**修复/验收**：真实运行缺数据返回 unavailable/failed，不产生推荐；demo 必须单独显式启用且不写真实实验索引。空目录、坏 CSV、缺列三种情形均应失败关闭。

### S2 · P1 · UI/CDaR 是旧 MDD 的倍数，未接入正式 MTM 评估

**位置**：`run_daily_local_optimization.py:150–175`；`run_two_stage_grid_optimization.py:134–150`。

daily 用 `UI=max(0.005, 0.45*MDD/E0)`、`CDaR=0.8*MDD/E0`；两阶段同样用 `0.45*MDD/1000`。这不能区分同最大回撤、不同水下时间的路径，正好绕过用户要求的新目标。`equity.py` 有 UI 函数，不代表候选选优调用了它；当前无精确复核阶段纠正这些估值。

**修复/验收**：按每个候选自己的完整权益路径计算风险。快速估值只能用于有标签的预筛；正式榜单必须引用精确 evaluation。两条同 MDD、不同回撤持续时间的候选应得到不同 UI，并能影响最终排序。

### S3 · P1 · 新协议的保证金、MDD、UI、交易数限制未执行

**位置**：`optimizer.py:150–188`；`run_daily_local_optimization.py:159–167`；`run_two_stage_grid_optimization.py:118–124`。

`select_best_and_recommended` 只检查候选自带 `is_feasible`，不按传入 protocol 重验。daily 只相信旧 CSV 的 margin 标志，缺字段还默认 true。两阶段仅筛正收益和保证金，注释明确无交易数限制。CLI 改保证金上限可能只改 protocol 标签，而没改变候选可行性。

**复现**：协议为 margin≤280、MDD≤20%、UI≤10%、至少30笔；传入 margin999、MDD90%、UI90%、1笔且旧标志为 true 的候选，仍被选为冠军。

**修复/验收**：建立唯一可行性判定，逐项保存拒绝原因；选优和 Pareto 都必须使用当前协议的结果。不同 cap 应有相应不同的可行集合；全部违规时返回无可行解。

### S4 · P1 · 真实第七维丢失，不同参数发生 ID 碰撞

**位置**：`run_daily_local_optimization.py:131–141,351`；`protocol.py:75–87`。

daily 读入时遗漏 `min_volume_ratio`，加入常量 `top_n_rank=10` 作为第七维。不同放量阈值的真实策略因此得到相同 parameter_id，后续 map 覆盖条目，历史“参数不变”失去意义。两阶段又使用原七维名称，两入口身份不统一；默认协议网格也与实际输入范围不一致。

**复现**：其余相同，仅放量阈值为 0 和 1.5 的两行，得到相同 ID `d35c1cba641dac5b`。

**修复/验收**：定义统一完整参数模型，保留单位与 Decimal 规范化，校验输入域；每个实际策略参数变化必须改变身份。禁止由展示字符串反推配置。

### S5 · P1 · 样本内冠军被写成实盘配置和样本外收益

**位置**：`run_daily_local_optimization.py:362–369`。

赋值明确为 `live_actual=daily_best`、`oos_forward_pnl=daily_best.net_pnl`。没有加载实盘完整配置生效段，也没有用昨天冻结参数评估新增未来区间。该字段不是“稍有误差”，而是不同概念。

**修复/验收**：从真实有效配置建立 live_actual；OOS 必须引用选择时间之前已冻结的参数与之后独立区间的评价记录。缺少其中一项就记 NA/insufficient_evidence。today-best、yesterday-forward、live-config 三者在测试中故意设不同，保存/报告仍应保持不同。

### S6 · P1 · 历史恢复与稳定判据都不成立

**位置**：`reporter.py:137–165`；`tracker.py:72–122`。

SQLite 读回时丢掉三轨候选对象，正常跨日运行会一直缺少历史推荐；查询还取最早30条而非最近30条。另一面，tracker 未使用 `min_oos_days=14`，无新快照去重、累计正收益、交易/活跃日、风险合规或回测可信门槛。

**复现**：保存完整三轨再读回，三者均 None；直接传入7条同一天同快照、零 OOS 的相同推荐记录，却返回 stable。前一个错误目前遮住后一个，不能只修历史恢复。

**修复/验收**：完整反序列化、读取最新窗口、有效日去重；以冻结前向评价和质量/风险证据驱动状态。重复运行、缺数据、负累计收益、风险违例都不能积累稳定资格。

### S7 · P1 · 邻域逻辑将正常数值网格全部判为满分

**位置**：`optimizer.py:115–128`。

判断写成 `key not in values`，例如字符串 key=`x` 不在数值 `[1,2]` 中，所有维度被跳过，空邻域返回 1.0。修正这个笔误后，缺失邻居仍可能被默认满分，需要一起解决覆盖率问题。

**复现**：唯一邻居不可行且亏损，当前稳定分仍为 1.0。

**修复/验收**：检查 `params[key]` 是否在网格，完整记录预期/已评估邻居数量、可行比例与收益退化；缺失证据不是满分。孤峰、平坦平台、网格边缘和缺邻居四类用例应可区分。

### S8 · P1 · 文件存在被当成完整数据和审计能力认证

**位置**：`snapshot.py:83–127`；`run_daily_local_optimization.py:327–357`。

snapshot 不解析实际时间，row_count 固定0；只要五个名称匹配的文件存在，就 complete 并授予 decision_replay_ready/execution_audit_ready。Parquet 内容不纳入整体快照内容身份；多账户目录只取第一个匹配文件。target_cutoff 只记录不核验；partial 也继续选优。

**复现**：五个空 CSV 得到 complete 和两个审计 ready 标签。

**修复/验收**：验证 schema、非空有效记录、账号、共同 watermark、质量缺口、历史选币及期初状态等实际依赖；按能力而非文件名授予标签。空文件、过期文件、错账号文件和截止未覆盖均应不能获得 ready。

### S9 · P1 · MTM 删除期末未平仓，也无法恢复期初持仓

**位置**：`mtm_engine.py:88–91,206–246`。

CSV loader 直接跳过 `closed=false`；TradeRecord 要求 exit_time，不能表示真正未平仓。窗口开始前的入场事件不会进入 active_trades，随后退出又因不在 active 中被忽略，导致整个期初持仓不入账。

**当前产物证据**：`optimization_all_collected_20260919/baseline_events.csv` 有9条已入场未平仓记录；`best_candidate_events.csv` 有21条，这些记录均被 loader 丢掉。不是只存在于理论边界。

**反例**：窗口前15秒以100开仓，窗口内以110平仓，100U名义、零费用，预期最终1010；实际1000，期间持仓数始终0。

**修复/验收**：支持可选退出和显式期初批次/挂单状态；按切点盯市计算区间收益。未平仓浮亏、跨日、跨窗口、配置变化中的持仓都必须保留。

### S10 · P1 · 15秒取整改变事件顺序和评估截止

**位置**：`mtm_engine.py:213–246`。

开平时刻都向下取整，再先平后开。同一桶内的开平仓会先尝试关闭不存在的持仓，然后开仓永久留存。即使不同桶，实际发生前就处理成交，破坏时间语义；结束时刻总多加一格，范围又包含该点，会读到请求截止之后的数据。

**反例**：00:00:01开、00:00:10平，预期已实现+10且0持仓；实际已实现0、仍1持仓。指定 end=00:00:30，最后一点为00:00:45。

**修复/验收**：真实事件顺序驱动账本，再按固定网格采样；同刻规则必须明确。不在请求截止之后处理事件，区间端点语义统一。

### S11 · P1 · 估值使用未来价格或无期限陈旧价格

**位置**：`mtm_engine.py:133–150,165–179`。

将桶的 close_price 标在 bucket_start，相当于把该桶结束才知道的值提前使用；查询早于首个报价时返回第一个未来价格。没有报价时返回入场价，后续缺口无最长陈旧时间，等同隐去该区间市场风险。还缺少环境、数据质量、重复/修订冲突检查。

**反例**：仅有30秒后的价格200，当前时间查询返回200而不是 unavailable。

**修复/验收**：明确 market_time/available_at，使用不晚于估值时刻的合格标记价；缺失超过阈值就降级/拒绝，不拿未来或入场价补真值。所有点保存价格来源和质量标签。

### S12 · P1 · 指标边界计算有确定错误

**位置**：`equity.py:124–127,196–221,301–318`。

CDaR 将线性插值分位数直接当作经验目标最小点，尾部样本不能整除时会高估，甚至超过 MDD。高水位只从首个观测权益开始，不包含传入的 E0：首点已经扣费/亏损时会隐藏初始回撤。日内统计把不完整日也直接计入，并以当日首个观测代替午夜权益。UI/水下占比按点数等权，没有验证等距；legacy 事件曲线与15秒曲线的 UI 倍数因此还混入不同采样权重。

**反例**：回撤 `[0,0.1]`、alpha=.95，真实最差5%尾均值应为0.1，代码返回0.145；E0=1000、两点都990，净亏10但 MDD 为0。

**修复/验收**：CDaR 用排序尾部及分数权重或正确经验分位；为权益序列建立一致初始锚点；验证时间排序、间隔和有限数；完整日才进日内汇总。覆盖少样本、重复分位、不规则采样、首点亏损及未恢复路径。

### S13 · P1 · 对账重复匹配，且未验证“同参数”前提

**位置**：`run_live_reconciliation.py:225–317`；同文件数据加载与 `reconciliation.py:74–285`。

CLI 用 symbol+90秒匹配信号、symbol+120秒匹配 BUY 成交，不消费已经匹配的实盘记录，也没有完整 account/run/config/side/intent 身份链。一次真实信号可以匹配多次回测；没有确定性配置生效区间和期初状态验证。另一套 matcher 即便可处理更多差异，也没有成为 daily 的统一对账接口。

**复现**：1条实盘信号/BUY 对2条同币种回测，L2 matched=2、precision=100%、recall=200%，L4成交匹配率100%。另对空输入调用 `reconcile_signals_and_fills` 得到 `is_audit_passed=True`。

**修复/验收**：确定性 ID 优先，受限一对一信号匹配和订单一对多部分成交聚合；歧义独立列出，零分母 NA，缺数据 unavailable。同参数和共同区间前提不满足时，不能输出一致性结论。

### S14 · P1 · 六层审计只做摘要，报告却生成无证据的成功归因

**位置**：`run_live_reconciliation.py:209–221,332–354,390–465`；`templates/dashboard_template.html:813,834`；`run_daily_local_optimization.py:394–395`。

用实际成交过的 symbol 集合代替历史 universe；fill到order映射率代替风险放行审计；卖出fill条数代替持仓批次校验。权益层只求已实现收益减手续费，未纳入余额、期初/期末浮盈亏、资金费及外部现金流。回测按入场落窗后把整笔净收益相加，还可能包括窗口外退出收益，与实盘按 fill_time 的口径不同。

报告无条件写“零意外拒单”“所有意图顺利放行”，缺信号统一归因于 universe 差异；模板固定展示资金费闭合/审计通过。daily 对账窗口固定为9月4日至14日，与每日报告日期脱节。看板也含9月18日固定窗口及缺目录时的历史回退（`dashboard.py:109–120,142–149,269–278,319`）；MTM对比又固定读取旧文件（`:607–609`），不遵循传入的equity CSV。新日期页面可能展示旧数据。

**修复/验收**：输出每层 observed/unknown/failed/passed，结论必须引用证据及统一窗口；未实现的层不能标通过。首个不匹配不自动等于已证实根因。构造订单缺失、手续费缺失、资金费缺失、跨窗交易时应显示对应缺口，而非成功文案。

### S15 · P1 · 三轨图使用缩放合成，不能证明推荐收益与回撤

**位置**：`dashboard.py:389–456`；`build_opt_groups.py:227–241`。

没有 profile 曲线时，拿一条基准曲线的累计收益比例乘固定353.43/356.39目标收益，并用 `max(0, progress)` 截掉低于起点的亏损。存在 profile 文件时又固定映射 D/F 为冠军/推荐，没有以参数 ID 核验。无约束组还直接把 daily_best 放到 recommended，并忽略实际算出的 res_none recommended。

**反例**：基准1000→900→1010，生成推荐1000→1000→1353.43。原本100U亏损被显示为不亏，终点则来自固定目标收益。

**修复/验收**：每条轨迹引用实际参数、区间、引擎、snapshot 对应的权益文件；缺任何轨迹显示无数据。图表总收益、MDD、UI 与同 evaluation 的结构化指标一致。

### S16 · P1 · 新增“真实 Top10”会沿用已经失效的成员

**位置**：`scripts/optimize_local_live_constrained.py:338–391` 及 `ProxyTop10.allows`；调用于修改后的 fast 优化/回放脚本。

构建器只为存在 rank≤N 的时点建立集合；某一时点无合格币种时不写空集合。之后 `allows` 向前查找，会继续沿用旧名单。异常文件也静默跳过；只存在少量 rank 数据不能证明整个历史拥有完整实际选币快照或实际激活时间。

**复现**：X在t0 rank1、t0+15秒rank11，Top10 查询后一时点仍允许X。

**修复/验收**：保留完整时间轴上的空集合、快照有效期与质量缺口；明确区分已知空池和未知覆盖，未知不无限向前延用。名称及报告中“exact/true”必须有覆盖及时间语义证据支撑。

### S17 · P2 · 不可变运行与每日可比身份未建立

**位置**：`reporter.py:99–135`、`protocol.py:32–56`、`run_daily_local_optimization.py:411–455`。

同 snapshot 名、同日同 protocol 用 INSERT OR REPLACE 覆盖；runs表仅建表，没有保存完整运行/evaluation的调用。Markdown按日期/场景复写，HTML只有日期，两个场景会互相覆盖。没有代码/指标/执行版本、选择时间、完整数据窗口与所有 trial 的可追溯关联。参数或输入变化后，旧结果可能不可恢复。

**修复/验收**：run_id独立于报告日期，数据修订另设 revision；协议保存真实搜索空间和执行/成本/代码语义；快照内容寻址；同日重跑/多场景均保留。所有“最优”标签说明完整网格或已评估子集，不能把旧 Top K 当全局最优。

### S18 · P1 · 批次重建会合并不同标的，汇总对账会跨账户配对

**位置**：`reconciliation.py:344–349,403–405`；`dashboard.py:327–331`。

部分成交聚合只以 order_id 为键，没有 account/symbol 命名空间；不同symbol相同order_id会被累加并覆盖标的信息。没有对应BUY的SELL被构造成“以卖价同刻开仓”的完整交易，而不是标记缺失期初仓位。FIFO成交配对也不等于项目定义的“平仓提交边界”批次。

看板将账户内结果处理完后，又把所有账户交易混在一起重新做不含account_id的匹配，可以将A账户实盘交易配到B账户回放。综合匹配率因此不能代表每个账户同参一致性。

**修复/验收**：按账户/交易所/symbol/order_id聚合，恢复真实批次边界；无开仓证据标记unknown/carry-in，不补造入场。总表汇总账户内匹配结果，不跨账户重新配对。用两个账户相反的漏单、两个symbol同order_id和窗口前开仓测试，必须保持错误可见。

Spec 轴计 18 项：S1–S16、S18 为 P1，S17 为 P2。最高优先级问题包括无数据生成成功结果、风险约束失效及前向/实盘身份混淆；这些会让后续统计和界面看起来成立，但没有相应证据。

### 正确性通过后的性能与维护优化

1. **读取缓存**：按 snapshot/参数/执行版本的内容键缓存特征与回放；避免每次绘图重新计算邻域、全表扫描。Parquet按日期/symbol投影过滤，不全目录无差别读取。
2. **事件驱动MTM**：当前重建每个15秒点遍历全部活跃交易，是Python循环，不是交付手册所称全向量化。先保持事件语义，再用按symbol聚合头寸和数组估值加速。
3. **Pareto**：当前两层循环最坏O(n²)，25,200候选约6.35亿次比较。优先先做合法约束过滤，再评估排序/分层前沿算法；保留同一输出语义与确定性。
4. **稳定区域而非单点**：修复邻域后记录覆盖率、边界、收益保留分布，并对近优簇做共同窗口行为比较。收益保留30%/40%阈值不能随入口改变。
5. **冻结验证与压力**：加入时间顺序walk-forward、成本/延迟/限价成交压力场景，以及连续日期分块的不确定性；不能把minute点数当独立样本。
6. **图表下采样**：展示可减点，但保留回撤极值和拐点；风险指标始终在全分辨率曲线上计算。每张图展示实际范围、配置、估值精度及能力标签。
7. **可交付性**：建立小而真实的端到端fixture，串起snapshot→replay→metrics→constraints→catalog→report；日报只在全部产物完成后原子发布，失败保留run状态和可恢复trial。

## 独立双轴审查摘要
