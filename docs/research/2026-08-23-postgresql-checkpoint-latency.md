# PostgreSQL Checkpoint Latency Research

Date: 2026-08-23  
Scope: current workspace at commit `4dacb73dfeaf2e53e03f239f96d8a0b76c4e0abc` and read-only production observations from PostgreSQL 16.14 on Tencent Cloud.

## Executive conclusion

The `write=434.179s` PostgreSQL log line is not, by itself, evidence that the disk wrote only about 31 MB in 434 seconds. PostgreSQL deliberately throttles checkpoint page writes to approach `checkpoint_completion_target`; the PostgreSQL source explicitly says `CheckpointWriteDelay` controls the write rate after each page write. With `checkpoint_timeout=15min` and `checkpoint_completion_target=0.9`, a checkpoint can intentionally remain in its write phase for a large fraction of 810 seconds. Reducing that duration by lowering `checkpoint_completion_target` would increase peak I/O and is contrary to the live-latency objective.

The dominant confirmed write amplification is the application strategy checkpoint, not the scheduled PostgreSQL checkpoint:

- Each strategy checkpoint stores complete rolling `MarketState15s` buffers in one JSONB value.
- Each current row contains 6.27–6.80 MB of JSON before PostgreSQL TOAST compression and 0.79–0.83 MB after `pglz` compression.
- Seven live/paper runs persist nearly identical market buffers independently.
- In roughly 13 hours, the checkpoint table recorded 5,305 updates; its TOAST table recorded 1,707,198 inserted and 1,706,448 deleted chunks.
- The live checkpoint repository uses the observability engine, whose pool has one connection and a one-second driver command timeout. A multi-megabyte JSONB parse/compress/TOAST rewrite is therefore expected to exceed the timeout occasionally on a shared 2-vCPU host.

The highest-return change is to make the strategy checkpoint compact and reconstruct market buffers from the canonical `runtime_market_states_15s` recovery store. This should reduce checkpoint payload writes by more than 98%, after which PostgreSQL tuning should be measured again.

## Important terminology

Two unrelated checkpoints are involved:

1. **PostgreSQL checkpoint**: the checkpointer writes dirty shared-buffer pages and establishes a recovery point.
2. **Strategy runtime checkpoint**: the application updates the single row for a strategy in `strategy_runtime_checkpoints`.

The first produces `checkpoint complete: ... write=...` logs. The second is the `UPDATE strategy_runtime_checkpoints ...` that hits the one-second command timeout and restarts `live-strategy`. Optimizing one number does not automatically fix the other path.

### Strategy checkpoint write amplification

Current row measurements:

| Run group | JSON text size | stored `pglz` size |
|---|---:|---:|
| live | 6.27 MB | 0.83 MB |
| paper runs | 6.71–6.80 MB | 0.79–0.80 MB each |

The payload is generated by serializing every state in every symbol's rolling market buffer. The default order-flow strategy needs 7 warmup buckets and stores `warmup + 16 = 23` complete states per symbol. All seven runs consume essentially the same canonical market-state stream, so this history is redundantly persisted seven times.

PostgreSQL stores large values in approximately 2 KB TOAST chunks. Changed out-of-line values incur new TOAST storage, while only unchanged out-of-line fields can be preserved without TOAST cost. The application changes the complete `payload` on every checkpoint, so the large value is rewritten every time.

Source: [PostgreSQL 16 TOAST storage](https://www.postgresql.org/docs/16/storage-toast.html).

### Hot market-state table and indexes

`runtime_market_states_15s` currently occupies about 1.52 GB, of which about 700 MB is indexes. It retains 48 hours and deletes 1,000 expired rows every minute. Every inserted and deleted row updates five B-tree indexes, including the primary key.

| Index | Size | scans since reset | Finding |
|---|---:|---:|---|
| polling `(environment, bucket_start, symbol)` | 164.9 MB | 513,173 | Required for ordered recovery/polling |
| symbol-time `(environment, symbol, bucket_start)` | 158.2 MB | 0 | Exactly duplicates primary-key columns |
| primary key `(environment, symbol, bucket_start)` | 157.8 MB | 358,266 | Required |
| created `(environment, created_at)` | 122.7 MB | 0 | No current source-code query found |
| latest bucket `(bucket_start) INCLUDE (bucket_end)` | 96.2 MB | 1,030,335 | Used by health/latest queries and retention |

The symbol-time index is structurally redundant. The created-time index is also a strong removal candidate, but should be observed over a longer representative window before removal. PostgreSQL supports `DROP INDEX CONCURRENTLY` to avoid blocking normal reads and writes.

Time partitioning by `bucket_start` would allow old data to be detached/dropped instead of deleted row-by-row. PostgreSQL documents that dropping/detaching a partition avoids the `VACUUM` overhead caused by bulk `DELETE`.

## Ranked optimization plan

### P0 — Measure the user-facing path, not checkpoint elapsed time

Define the pass/fail target around the strategy checkpoint and live process:

- no `live-strategy` restart caused by checkpoint persistence;
- periodic checkpoint persistence p95 below 250 ms and p99 below 1 s;
- no order-intent-to-submit latency regression while a PostgreSQL checkpoint is active;
- checkpoint payload stored size below 50 KB per run;
- TOAST insert/delete rate reduced by at least 95%.

Before changing database tuning, add or enable:

1. Application timings for checkpoint construction, JSON serialization, pool acquisition, SQL execution, and commit.
2. `track_io_timing=on` and `track_wal_io_timing=on` after checking timing-call overhead with `pg_test_timing`.
3. `pg_stat_statements` during a planned PostgreSQL restart so the checkpoint UPDATE's execution time, blocks, and WAL can be measured directly.
4. Tencent Cloud 10-second disk metrics around an actual timeout.

Sources:

- [PostgreSQL 16 I/O timing and `pg_stat_io`](https://www.postgresql.org/docs/16/monitoring-stats.html)
- [PostgreSQL 16 `pg_stat_statements`](https://www.postgresql.org/docs/16/pgstatstatements.html)
- [PostgreSQL 16 `pg_test_timing`](https://www.postgresql.org/docs/16/pgtesttiming.html)

### P1 — Compact strategy checkpoints (highest expected return)

Do not persist `market_state_buffers` independently for every strategy. Persist only non-derivable control state:

- last processed timestamp per symbol;
- cooldown state;
- signal sequence/idempotency cursor;
- schema/version and the exact recovery boundary.

At startup, reconstruct the last `warmup_buckets + 16` states per symbol from the canonical `runtime_market_states_15s` table up to the saved recovery boundary, without emitting orders during warmup. Then subscribe to the Hub and discard states at or before the restored cursor.

This keeps deterministic restart behavior while removing repeated 6–7 MB JSON documents. Based on current row sizes, the durable checkpoint should fall from roughly 800 KB compressed to well under 20 KB, a reduction comfortably above 98%. It also removes PostgreSQL JSON parsing and `pglz` compression of roughly 6–7 MB per save.

If exact buffer reconstruction cannot be made deterministic immediately, an interim design can persist one shared market-buffer snapshot per environment/bucket and let all strategies reference it. That still removes seven-way duplication.

### P1 — Remove checkpoint persistence from the live decision loop

Use a dedicated checkpoint writer with a one-item, last-write-wins queue:

1. The strategy loop constructs or publishes the latest compact checkpoint without awaiting database I/O.
2. One background task coalesces obsolete pending checkpoints.
3. Periodic checkpoint failure is logged and retried; it does not terminate `live-strategy`.
4. Final shutdown and ambiguous-order recovery checkpoints use a bounded, explicitly handled critical path.
5. Checkpoint and telemetry use separate one-connection pools; telemetry retains its 250 ms best-effort timeout.

Use a single `INSERT ... ON CONFLICT DO UPDATE` instead of `SELECT` followed by `UPDATE`. Give the checkpoint connection a realistic 5–10 second safety timeout, but treat that as containment rather than the performance fix.

### P1 — Remove redundant market-state indexes

1. Drop `ix_runtime_market_states_15s_symbol_time` concurrently after an automated plan/behavior check; the primary key has the same columns in the same order.
2. Continue observing `ix_runtime_market_states_15s_created` for 24–72 representative hours; if it remains unused and no operational query requires it, drop it concurrently.

Removing both would eliminate about 281 MB of index storage and reduce index maintenance on every insert and retention delete by roughly two of five indexes.

### P2 — Replace row-delete retention with time partitions

Range-partition `runtime_market_states_15s` on `bucket_start`, using a partition width appropriate to the recovery horizon (for example six hours). Create future partitions ahead of time, detach expired partitions concurrently, then drop detached tables. This removes the continuous 1,000-row-per-minute delete stream and most related vacuum/index cleanup.

After deterministic recovery is validated, reassess whether PostgreSQL needs 48 hours of market states. Live startup currently needs only a bounded warmup window; raw archives remain the durable research source. A shorter operational horizon further reduces the active table and index working set, but partitioning should precede a large retention reduction.

### P2 — Tune PostgreSQL only after reducing writes

Change one variable at a time and compare 30–60 minute counter deltas:

1. Keep `checkpoint_completion_target=0.9`; do not lower it to make the log duration look shorter.
2. Keep the current 15-minute checkpoint interval and 2 GB `max_wal_size` until post-change WAL rate is measured.
3. Test `bgwriter_lru_maxpages=400` while keeping `bgwriter_lru_multiplier=2.0`. Success means lower `buffers_backend` growth and near-zero `maxwritten_clean` growth without worse disk await.
4. At a planned restart, test `shared_buffers=256MB` (25% of PostgreSQL's 1 GB cgroup limit) and `wal_buffers=16MB`. Monitor host swap activity and container memory headroom.
5. Test `wal_compression=lz4` if the packaged server supports it. It reduces full-page-image WAL at a CPU cost; compare WAL bytes per minute and CPU.
6. Optionally set checkpoint payload TOAST compression to LZ4 as an interim CPU optimization, but do not use compression as a substitute for deleting the redundant payload.

PostgreSQL warns that smaller background-writer limits make client backends more likely to write dirty buffers themselves, delaying interactive queries. It also suggests 25% of memory as a reasonable `shared_buffers` starting point on a dedicated database host, while retaining operating-system cache headroom.

Source: [PostgreSQL 16 resource consumption and background writer](https://www.postgresql.org/docs/16/runtime-config-resource.html).

### P3 — Upgrade the existing cloud resource only if metrics prove saturation

No additional physical disk is required for the first two phases. If Tencent monitoring shows the system disk repeatedly reaching IOPS/utilization limits or high await after write reduction:

- enlarge or migrate the existing system disk to a faster supported class;
- move to a newer CVM generation with a higher storage-performance ceiling;
- or move PostgreSQL to a managed/dedicated endpoint later.

Tencent Cloud ties baseline disk performance to disk type and, for several types, capacity. Its documentation also notes that system disks have different upgrade restrictions from elastic data disks, so the exact console operation depends on the current system-disk class.

## Changes that should not be used as the fix

- Do not lower `checkpoint_completion_target` merely to shorten the logged duration; it increases peak checkpoint I/O.
- Do not disable `fsync` or `full_page_writes`; PostgreSQL documents corruption risk after a crash.
- Do not run `VACUUM FULL` during live operation as a latency remedy; it locks and rewrites the table and does not remove the source write stream.
- Do not treat a longer application timeout as the complete fix; it only delays failure.
- Do not disable order-lifecycle telemetry first. Current durable telemetry is already sparse, asynchronous, and uses `synchronous_commit=off`; the multi-megabyte strategy checkpoint is much larger.
- Do not tune `effective_io_concurrency` expecting it to shorten checkpoints; it primarily affects supported asynchronous read/prefetch paths.

Source for durability constraints: [PostgreSQL 16 WAL reliability and settings](https://www.postgresql.org/docs/16/runtime-config-wal.html).

## Recommended implementation order

1. Add checkpoint path timings and a no-restart regression test.
2. Compact the checkpoint and reconstruct market buffers from canonical states.
3. Move periodic checkpoint persistence to a coalescing background writer with a dedicated pool and non-fatal retry semantics.
4. Replace read-then-update with one upsert.
5. Drop the exactly redundant symbol-time index concurrently.
6. Measure for at least one representative hour.
7. Tune background writer/WAL/shared buffers one variable at a time.
8. Plan market-state partitioning and shorter operational retention.
9. Consider cloud resource upgrades only if measured storage limits remain.
