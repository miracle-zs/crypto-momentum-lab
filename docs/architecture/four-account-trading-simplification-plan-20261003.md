- 日期：2026-10-03（Asia/Shanghai）。
- 状态：本地实施与回归中；2026-10-04 修复复查遗漏，未部署。性能与部分架构验收仍待完成。
- 编写基线：`61758ecece9d80b61367dd8cdc79f082f59437aa`。实施前重新核对工作区和生产版本。
- 部署目标：保留 11 个常驻应用进程、4 个交易账户；优先简化进程内部规则、事务和状态维护。
- 数量依据：仓库部署配置，未在本次验证服务器实时容器数量。
- 历史关系：本计划是后续整理计划，不覆盖既有实施记录，也不将历史审查问题自动认定为当前版本缺陷。

## 1. 部署基线与范围

| 常驻应用 | 数量 | 作用 |
| --- | ---: | --- |
| 策略与订单执行 | 4 | 每账户独立运行策略、风险计算、订单执行及恢复 |
| 账户同步与 Account Hub | 4 | 每账户独立采集账户事实并提供事实流与控制通信 |

本轮不合并上述部署，不引入新消息中间件，不重写策略算法，也不以删除固定比例代码为目标。账户内实现由四账户复用，账户数据和控制权保持隔离。共享数据库、主机、行情及网络仍是共同依赖，进程分离不等于完全故障隔离。

既有 [实盘运行简化计划](live-runtime-simplification-plan-20261003.md)、[完成度复查](live-runtime-simplification-completion-review-20261003.md)和[交易执行安全修改计划](system-overengineering-modification-plan-20261003.md)保留历史意义。本计划实施时先辨别已完成内容，避免再次构建被删除的账户模式或重复改造。

## 2. 目标与必须保留的业务约束

目标是让正常订单沿少量接口完成，让维护者能在一个位置修改同一规则。模块内部可以保留复杂实现，但调用方不应了解多仓储提交顺序、补偿步骤和恢复细节。框图中的职责不代表必须新增同名类。

必须保持：

1. 账户隔离：订单、成交、风险基线、额度、预留、租约、缓存和恢复请求均包含正确的账户身份。
2. 在途及未知开仓占用风险额度；未成交订单不能因持仓未变化而漏算。
3. 同账户不同 symbol/方向的额度裁决是原子的；空账户没有 claim 行时也必须有可锁定的账户仲裁记录或既有等效锁。
4. 候选有效期与 `projection_version` 分别验证时间和依据，两者不能互相替代。单仓位版本也不能替代账户总敞口基线。
5. 数量/价格符合交易规则；最终计划估值不超过批准额度。市价实际成交价格变化由明确的估值和风险政策处理，不宣称 floor 能保证实际成交金额硬顶。
6. 入场限制不误施加于退出；退出仍检查身份、方向、数量分配和必要控制权。沿用现有明确的退出授权政策。
7. 命令身份、真实成交、累计水位与重复观察保持幂等；UNKNOWN 不能自动重发或直接释放占用。
8. 单账户局部恢复不阻塞其他账户；某 symbol 缺少事实时，限制依赖这些事实的动作。无法界定账户风险时限制新增风险，继续事实消费和证据充分的退出。
9. 数据库事务不跨 HTTP、Hub 等待或限频等待。

默认保留现有每账户风险口径，不新增四账户合计额度。若当前数据库配置已有组合级限额，保留并单独明确其仲裁范围。

## 3. 目标正常链路

```text
共享 Market Hub
  → 账户策略进程：更新指标、产生候选
  → 绑定候选有效期、持仓版本和必要风险基线
  → 统一风控计算、价格选择、数量量化
  → 按账户 + symbol + position_side 排队
  → 出队：取消/有效期/版本/动作授权检查
  → 单次本地准备事务：额度仲裁、数量预留、订单与命令关联
  → Hub 提示等必要准备、限频等待
  → 最新动态控制检查
  → HTTP 提交
  → 订单/账户事件吸收，推进真实账本并结算占用
```

持久化决策提交若承担策略状态和退出 outbox 的原子推进，先保留；修正结果释放契约后再评估其简化方式。策略计算、风险计算及量化尽量是同步纯计算；必要持久化和网络调用有明确 await 位置。

控制检查统一规则来源，但保留有不同职责的时点：入口决定是否产生可执行候选，出队淘汰失效候选，事务裁决权威额度，最终请求前校验最新动态控制事实。检查通过不代表可以删除该检查。

## 4. 分阶段执行

### P0：核对当前事实并建立基线

工作：

- 只读核对实际部署版本、11 个应用的启用情况、账户映射及未决订单。配置数量与实时数量分别记录。
- 列出当前准入和状态规则；尊重已有 RUNNING/局部限制改造，不重新引入全账户软状态开关。
- 确认 FIFO 还是定向批次核销、同 symbol 在途并发数、退出授权、TTL、金额口径和价格新鲜度政策。未明确的规则保持现状并记录，不顺便改策略。
- 逐项检查早期审查报告：已修复、当前仍可复现、待验证。不能引用历史测试数量作为当前安全证明。
- 测量正常链路分段耗时、事务数、SQL 数、数据库连接等待、事件循环延迟及队列深度；按账户记录。

### P2：统一准入与风险规则

工作：

- 集中 `FixedLiveLimits`、`RiskGateway` 和提交侧重复规则；返回批准额度、拒绝原因、作用域及必要版本。
- 保留队列/生命周期职责，移除 EntryLane 等调用方内重复的额度和软状态解释。
- 确定一次参考价格及其来源、时间；风控和计划编译使用相同依据，下游不自行增加隐式价格回退。
- 静态配置身份预计算；动态审批、人工暂停、有效租约继续取真实事实。
- 核对 CapabilityEvaluator 每个输入的来源和用途；删除无独立语义的重复判断，不用常量证明采集健康。
- 四账户共享代码，使用各自事实；跨进程的控制变化继续由现有 Hub/数据库机制传达。

验收：每项限额和动作许可只有一个规则实现；开仓和退出的差异明确；修改一项规则不用同步改多个调用方；最终围栏不以单个进程内布尔值替代跨进程控制事实。

### P3：清理正常热路径

工作：

- 普通遥测走既有有界队列和统一消费者；若目前已旁路，只检查仍残留的等待。重要订单事实不降级为可丢遥测。
- 队列满、取消、停机和持久化重放沿用明确策略；不每单随手创建后台 Task。
- 杠杆、保证金模式、规则在账户标的启用前预热；未完成的标的暂不开新仓，由后台初始化。
- 缓存必须区分账户；保留配置变更、规则变化和缓存失效机制。
- 去掉重复对象转换、无用途摘要和纯转发层。保留实际使用的诊断字段。
- 保留跨容器共享请求节流，确认账户隔离和共享 IP 等资源的节流范围，不因进程内优化让总请求失控。

验收：正常订单不等待可选遥测或冷配置；监测队列有界且资源能清理；按账户比较延迟，不预设百分比收益。

### P4：统一订单准备事务

工作：

- 让调用方只提交一次准备请求；沿用既有 Book/UoW/仓储内部实现，减少调用方必须了解的顺序。
- 明确可合并的写集合：命令关联、开仓额度占用、退出数量预留、订单准备记录及必要 head/version。
- 在同一个执行数据库事务中完成账户额度仲裁与这些关联写入；实施前确认数据库配置确实支持同一事务。
- 固定锁顺序；账户级额度跨 symbol 串行裁决，position 级事实有自己的锁，不能仅靠各 Worker 队列。
- 保持内存 staged copy 在提交成功后发布；事务取消或提交确认不确定时有明确重载/封锁策略。
- 保留“准备完成”和“开始外部提交”的必要语义；是否减少 DISPATCHING 持久化步骤，通过取消与重启测试决定。
- 删除仅为本地准备写入割裂而存在的补偿分支；外部提交 UNKNOWN 与恢复继续保留。

验收：任一步本地准备失败不留下无对应准备订单的新增额度/数量占用；重启可识别已准备未发、可能已发和已确认订单；事务/SQL 往返实测下降，不能宣称固定 5ms 或无死锁。

### P5：统一终态吸收，评估冗余状态

先统一事实所有权，再删表：

| 事实 | 目标权威来源 |
| --- | --- |
| 意图/命令幂等身份 | 持久化唯一约束及明确身份关联 |
| 订单状态和累计成交 | 订单读模型 |
| 真实成交 | 不可变成交记录及 durable trade identity |
| 持仓及批次 | 真实成交和账户覆盖证据派生的账本 |
| 尚未被风险基线覆盖的开仓风险 | 一套明确的额度交接记录或可证明的计算 |
| 已分配的退出数量 | 一套数量预留记录 |

工作：

- 评估 IntentClaim 是否可由已有唯一约束取代；确认所有调用路径后再删除。
- ExposureClaim 保留未入基线的风险交接语义；可并入订单关联数据，但不能只用“当前持仓”替代。
- EpisodeReservation 若能完全从命令和数量预留推导，移除冗余维护；不能推导则记录独立用途。
- 本地 pending 缓存改为可从权威记录重建的派生数据。
- 尽可能让事件去重、订单推进、相关占用、账本事实及版本在一次事务内接受。
- 如账本必须后续处理，使用可靠的持久化待处理机制，避免事件提交后仅依赖一次内存回调。
- 不凭终态释放已成交但未被基线覆盖的风险；不凭订单累计量虚构真实成交。

验收：同一事实重复观察结果不变；迟到 ACK 不回滚终态或误释放；成交晚于终态到达仍能核销；事务失败/重启能补齐而不重复 POST；FIFO 等策略语义保持 P0 已确认规则。

### P6：收敛恢复与内部并发

工作：

- 恢复对调用方只提供请求、状态与启动恢复等少量接口；positions/orders/exits 的分类保留在内部实现。
- 复用已有请求驱动调度，合并重复查询和恢复请求，明确预算、退避及长期 pending 原因；不新增固定周期全量 REST 扫描。
- 四账户恢复相互独立；同账户局部缺口不无条件关闭其他 symbol。
- 如实命名 Book 级全局锁：先确认每个策略进程中的 Book 实例归属。当前每账户独立进程，不能误称一把 asyncio 锁横跨四账户。
- 只有账户内吞吐测量证明必要、staged copy 及发布状态已隔离后，才细化 position 锁。
- 保留防重复启动和租约接管围栏；四账户部署不是删除跨进程控制的理由。
- 迁移后删除旧接口、未使用适配器和重复配置路径，保留实际部署需要的账户/进程能力。

验收：一个账户网络或恢复延迟不阻塞其他策略进程；一账户局部问题不扩散为无依据的全账户阻断；新旧重复实例无法同时获准提交；恢复入口简单且内部行为可追踪。

## 5. 实施顺序与验证

顺序为 P0 → P1 → P2 → P3 → P4 → P5 → P6。P4/P5 可以按开仓、退出和事件吸收拆成更小提交，但必须逐项记录中间契约，避免双重占用。优先完成 P0–P3，再进入事务和状态结构迁移。

| 验证层 | 必须证明的行为 |
| --- | --- |
| 正常路径 | 四账户正常消费行情；开仓/退出按各自配置执行；风险和量化结果一致 |
| 账户隔离 | 相同 symbol 和相似订单标识不串账；暂停 A 不暂停 B；缓存、恢复和资金基线不跨账户 |
| 同账户并发 | 不同 symbol 同时使用旧基线准备，仍不会突破额度；同批次退出不重复分配 |
| 基本失效窗口 | 排队取消、候选过期、版本变化、限频期间撤权能得到明确处理 |
| 外部未知结果 | POST 后超时/解析失败不错误释放、不自动重发；后续事实可收敛 |
| 事件交错 | 重复/乱序、部分成交撤单、成交晚到、账户基线先后更新均幂等 |
| 重启/事务 | 各本地提交阶段崩溃可恢复；占用和订单关联一致；提交确认不确定有处理 |
| 性能与资源 | 分账户的延迟、SQL、连接等待和 Event Loop 延迟；有界遥测和共享限频可控 |

扩展现有行为测试，测试通过模块接口验证业务结果；删除旧结构断言时，以对应业务约束替换，不为每层转发增加镜像测试。跨进程和数据库锁使用真实 PostgreSQL、实际交错或可控传输验证，不能只靠 mock。文档变更仅检查差异和链接；实现阶段按改动范围运行测试与静态检查。

性能采样区分自然负载和可重复负载；记录输入量、账户在途数量、数据库状态、提交版本和采样时长，比较 p50/p95/p99，不将自然行情变化当作优化收益。不为验证主动发送未授权的实盘订单。

## 6. 发布与回退

1. 每阶段独立提交，明确行为变更、验证结果和未覆盖内容。
2. 数据结构迁移遵循先兼容读旧数据、再切换写入、后清理旧数据结构；验证回滚版本仍能读新产生的订单及占用。
3. 持久化事实和幂等身份不双写两套权威实现；临时对比可以只读计算，不能双发订单。
4. 发布前再次核对生产账户/进程/版本、未决订单和数据库配置；按现有授权流程实施，文档编写不等于授权部署。
5. 只有新旧数据库和 Hub 协议兼容时才按账户逐步发布；不兼容时必须先完成适配迁移，不能直接滚动混跑。
6. 对一个账户的验证不自动代表四账户隔离验收；完成后检查四账户和共享资源。
7. 回退不删除真实订单、成交或预留来“恢复干净状态”；使用兼容版本和已有恢复路径。
