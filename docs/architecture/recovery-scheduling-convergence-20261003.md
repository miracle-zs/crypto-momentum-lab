# 对账调度收敛：2026-10-03

## 问题与复现

普通账户快照、成交在写入账本后，原来无条件调用
`LiveOrderReconciliation.request_recovery()`。这个请求会检查仓位修复、恢复中的
执行命令、未决订单和持久化退出，并不等于每次都请求交易所，但会造成重复工作。

执行命令恢复与未决订单扫描还会分别查询同一个未知订单。查询仍未解决不确定性时，
同一轮修复会重复调用 `Coordinator.reconcile_order()`。

回归入口：

```bash
rtk proxy .venv/bin/python -m pytest -q tests/unit/live_rollout/test_recovery_scheduling.py
```

修改前复现：20 次普通账户更新造成 20 次未决订单扫描；同一未知订单单轮补查
2 次。两项断言均失败。

## 本轮实现

账户事实提交后调用 `notify_account_facts_changed()`：只有已经请求、正在执行或
仍未完成的修复会被唤醒。正常事实更新不能创建恢复任务。启动恢复、订单状态不明、
未托管仓位和持久化退出仍通过显式 `request_recovery()` 创建任务。

修复执行中的事实更新保留一次后续唤醒，多个更新由现有 `asyncio.Event` 合并。
未完成工作保留原有定时重试；完成后任务休眠。未托管仓位修复现在明确返回是否
还有待处理工作，避免收窄触发后依赖后续普通账户更新才能继续。

命令恢复与未决订单扫描共享单轮订单补查函数，按 `client_order_id` 去重。
只有补查与结果应用成功后才记为已查询；去重集合在下一轮重新创建。
恢复失败仍暴露给原有修复任务的错误报告与重试机制，不永久缓存失败或未知结果。
已持久化的终态回执仍可直接结算，无需交易所查询。

没有新增后台任务、数据库表或跨轮订单缓存。账户服务的权威成交扫描、断线恢复、
发单事务边界与退出恢复专用通道保持原有契约。

待处理退出随新事实继续、执行中事实更新的唤醒合并、仓位修复独立定时重试。
