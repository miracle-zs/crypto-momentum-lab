# 恢复任务按职责收敛

## 问题与复现

第一步阻止了普通账户事实创建恢复任务，但已有任务仍共用一个 pending 标志。
仓位、订单或退出中只要任一恢复未完成，下一轮会重新执行所有恢复，包括已完成的
仓储扫描。第二步的等待结果分类没有改变这个调度行为。

复现命令：

```bash
rtk proxy .venv/bin/python -m pytest -q tests/unit/live_rollout/test_recovery_task_scopes.py --tb=short
```

修改前，三种“只有一类未完成”的场景均失败：预期调用次数为 `2 / 1 / 1`，
实际为 `2 / 2 / 2`。根因是待办状态没有记录恢复的职责种类。

## 实现与边界

保留现有单个恢复 worker，分别保存请求中的任务、当前执行中的任务以及各类任务
的重试截止时间。仍按仓位、订单、退出顺序串行执行；没有增加后台任务或并发发单。

| 触发源 | 入口 | 恢复范围 |
| --- | --- | --- |
| 启动或显式全量修复 | `request_recovery()` | 三类恢复各做一次发现 |
| 不完整 WS 订单事实或 UNKNOWN 订单事件 | `request_order_recovery()` | 执行命令与未决订单 |
| 持久化退出、退出管道请求 | `request_exit_recovery()` | 退出所有者 |
| 未托管仓位上下文 | `request_position_recovery()` | 仓位修复 |
| 新账户事实 | `notify_account_facts_changed()` | 只唤醒仍待办或执行中的恢复 |
| 重试时间到期 | worker 内部 | 只重试到期且未完成的恢复 |

当前轮开始前消费请求集合，执行期间到达的请求留给下一轮；重复请求合并。
任务完成后清除其执行中状态，不再随其他任务的新事实通知重复恢复。
各类任务使用单调时钟保存独立截止时间，频繁退出请求不能重置未知订单的重试期限。
同一 worker 中的慢 I/O 仍会延迟后续任务，这里没有承诺不同恢复并行执行。

各类恢复异常保留完整错误日志和 `recovery_task`，只将失败的任务保留为待重试。
订单恢复失败不再跳过当前轮已请求的退出恢复；取消仍向外传播。

通用订单发现将未知平仓单成功交给退出所有者时，明确请求退出恢复，不再仅凭
该条订单保留通用订单扫描。若命令账本另有待结算状态，命令恢复仍可保留订单任务。
退出专用恢复与命令恢复之间所有远程查询的进一步合并不在本次范围。

这一步按任务种类收敛。仓位修复仍读取上下文中的未托管 symbol 集合，退出恢复
仍使用各自待办；尚未引入按 PositionKey 分配截止时间或过滤事实唤醒的机制。

## 验证

新增 13 项回归，覆盖三类独立重试、三类显式请求、重复请求合并、执行中新请求
保留、三类失败隔离、退出请求不饿死订单重试、不完整 WS 仅请求订单、未知平仓
单转交后仅由退出所有者重试。调整第一步的一项断言：待退出恢复被新事实唤醒时，
已完成的订单扫描应仍只有一次。

全量单测默认运行 **3221 项通过、4 项网络测试跳过**，耗时 38.81 秒；另以
`CML_RUN_HUB_NETWORK_TESTS=1` 执行两个 Hub 文件，**52 项通过**，包含上述
4 项网络测试，因此全部 **3225 项单元测试已验证通过**。保留既有 Starlette
弃用与异步生成器关闭两项警告。核心调度与新增测试通过 Ruff，orchestrator 的
检查保留对已有长行的 E501 忽略；核心调度通过 Mypy，差异空白检查通过。
