# 系统复杂度与简化审查（2026-10-01）

审查基准：main，b5bfc801。此前模块解耦和最新周期检查改动均计入本次审查。

## 结论与范围

值得重构的复杂度主要集中在实盘运行层的状态读取、账户事件消费、退出恢复和配置装配。优先减少状态来源、同步等待和恢复入口，而不是继续按文件长度增加模块。领域账本、订单幂等、共享行情和异步 checkpoint 各有明确业务用途。

对 src/crypto_momentum_lab 的 400 个 Python 模块进行 AST 结构及绝对内部 import 扫描，重点人工核对实盘账户/订单事件、上下文装配、退出恢复、入场门槛、checkpoint、行情采集/广播、Dashboard 及研究采集。没有逐行审查所有实现，没有访问服务器，没有进行生产故障复现或性能测量。本报告仅新增文档，未改变交易行为；上轮 1,364 项测试结果不能视为本报告各建议的验收。

结构信号：live_rollout 包有 85 个模块、27,929 行；run_live_daemon 跨 1,542 行；live run CLI 有 54 个具名参数。领域包没有扫描到指向其他顶层业务包的绝对内部 import。行数、模块数及动态探测数量仅用于定位审查对象，不作为过度设计或业务故障的证明。

P1/P2/P3 表示本报告的重构优先级，不代表已经确认对应级别的生产故障。

## 优先重构项

### 1. P1：账户事实消费先等待 REST 与业务重试

证据：live_rollout/account_channel.py:104 在 ORDER_TRADE_UPDATE 上先 await reconcile_account_event，:117 才调用账户快照/事实应用；order_reconciliation.py:50 查找订单后调用 reconcile_order；orders/state_machine.py:360、:568 最终执行交易所订单查询及重试。account_channel.py:133 的持仓同步失败在同一消费者内逐次 sleep，runtime_config.py:28配置 0.25、0.5、1、2、4、8、16、32 秒，合计 63.75 秒，不含数据库和网络耗时。

这是可确认的串行依赖。慢查询、未决订单或同步等待会拖慢后续账户事件消费；底层 reader 与缓冲队列仍可继续接收，不能据此声称服务器已经停收或丢失消息。独立行情/退出通道也不能等同于全部暂停。

简化方向：有效 WS 订单事实进入现有订单状态机和执行 Book，由同一订单身份完成幂等应用；未知身份、缺字段及查询结果不确定时才安排独立查询。账户事实消费者只完成必要事实提交及按持仓有序的交接，不在消费循环中等待多轮业务恢复。必须保留“入场成交和订单身份先于持仓授权可见”的原子/顺序要求，不能直接把现有 await 改为无监督 create_task。

验收：REST 查询阻塞时后续有效账户事实仍被接收并提交；同一持仓的订单与成交不会乱序授权；重复 WS/REST 成交不重复计量；未知身份仍限制新增风险；退出恢复不会重复提交订单。

### 2. P1：交易状态在运行层与 Dashboard 重复推导

证据：entry_control.py:12 维护动态入场门槛；gates.py:41 验证批准和运行条件；risk/gateway.py:37 在提交意图前执行风险判断；readiness.py:41 将门槛映射为交易模式。operator_dashboard/overview_queries.py:300 附近又推导账户 capability，:438 起再根据数据库、流状态、账户状态与租约独立计算 FULLY_TRADEABLE/EXIT_ONLY 等模式。

最终提交时复核租约、批准及风险限额有真实用途，不能删除。冗余在于展示层另行拥有一套“实际能否交易”的判断；该概括未完整使用运行层的预热、退出失败、缓存与待同步持仓等门槛。存在状态解释漂移的结构风险，本次没有复现某个实际误报。

简化方向：实际门槛及其原因由运行层发布一个带版本和观测时间的结果，Dashboard 展示该结果与它的新鲜程度；无法取得结果时明确未知/过期。系统汇总可以聚合各账户结果，但不能把汇总状态当作每个账户的授权。提交时的风险复核仍保留。

验收：预热、退出失败、待同步持仓、租约过期等场景中，展示原因与实际拒绝原因一致；账户 A 异常不误报账户 B 的独立能力；缺失发布结果不能推断可交易。

### 3. P1：完整上下文有多份缓存及多轮失效校验

证据：runtime_orchestrator.py:1283、:1295 分别构造交易与心跳 PostgresLiveContextProvider，:1307 将同一 ExecutionBook 注入两者；control_plane.py:212 起向两者传播账户更新。postgres_runtime.py:225 起在锁前和锁内多次检查 cache epoch、桶时间、观测时间及缓存，:556 起加载批准、风险配置、租约、halt、订单和持仓。context_prefetch.py 又用 generation 防止预取结果过期，退出通道也按事件重新获取上下文。

隔离心跳数据库资源可避免慢业务查询影响租约续期，值得保留。问题在于两套完整账户/订单上下文及多层缓存共同维护有效性，迫使调用方同时理解多种失效标记。不能未经测量就断言数据库当前负载由此造成。

简化方向：共享只读的 WS 账户视图和 Book 投影；把租约、批准、风控配置作为独立控制事实。交易上下文由这些带版本的值一次组装；心跳只读取续租所需控制事实，不再加载完整交易上下文。数据库资源隔离继续有效。减少整个上下文的 TTL/epoch/cache 副本，而不是新增一个聚合缓存再保留旧缓存。

验收：账户更新期间预取结果不能授权新订单；续租不等待交易查询；同一轮事件只使必要视图失效；入场和退出读到相同持仓版本。

### 4. P1：退出恢复分散在多种对象中

证据：decision_facts.py:466 恢复决策退出 outbox；exit_receipt_recovery.py:71 起核验退出回执，:119 附近维护独立五秒账户 REST cut；exit_processor.py:307、:349 恢复 UNKNOWN 退出订单，自己维护尝试次数、退避和锁；order_reconciliation.py:86 周期核对未决订单；runtime_orchestrator.py:1628 在账户事件处理后又触发 pending exits 恢复。

这些对象恢复的是不同阶段，不能直接认定为同一工作执行了多次，也不能删掉某一种状态。复杂度来自恢复触发、交易所查询、退避和事实同步散落在多个所有者中。

简化方向：一个退出恢复入口按稳定 command/order 身份协调决策 outbox、订单回执和 Book 状态；其内部保留各阶段不同的终结证据。行情、账户事件和定时器仅触发这个入口；统一每订单查询预算及退避。明确区分“命令未发”“回执未知”“已成交但本地未结算”，不能凭空仓或订单缺席直接清除未决记录。

验收：并发触发恢复只产生一个有效尝试；部分成交、取消超时及进程重启保持数量守恒；空仓但回执未知的记录仍受保护；恢复入口不阻塞账户事实消费。

### 5. P2：生产契约仍保留运行时兼容探测

证据：ReadOnlyAccountClient 在 sync_ports.py 明确声明 include_flat 和成交 provenance，但 client_compat.py:14 用 inspect.signature 判断 include_flat，:28 又把 provenance 当可选能力；daemon.py:50 检查心跳参数形状，周期检查也为缺少能力的旧适配器走另一条修复路径。生产 apps/execution_account/main.py 装配的是 BinanceUsdMPrivateReadClient；测试中的旧 fake 不应永久决定生产流程。

AST 扫描 live_rollout 有 170 个 getattr、7 个 hasattr，execution_account 有 46 个 getattr、4 个 hasattr。其中包括正常的载荷/ORM/可选值处理，不应整体删除，也不把数量等同于兼容分支数量。

简化方向：生产必须具备的能力直接通过明确接口调用，装配时验证一次；同步更新实际适配器和测试 fake。真正支持不同部署能力时，在装配处选定明确适配器，不让核心流程在每次事件中猜方法形状。

验收：生产必需能力缺失时启动明确失败；支持的适配器行为一致；不把缺少必要能力伪装为安全 fallback。

### 6. P2：最新简化留下尚无生产调用的 checkpoint 能力

证据：目前 baseline_checkpoint 的构造/注入调用只出现在测试；生产 daemon 已没有候选 checkpoint 生成流程。sync.py:150 的日志游标门面、仓储 load_baseline_checkpoint 和相应序列化写入支持仍存在，但没有当前生产自动恢复消费者。

这是此前阶段演进留下的具体冗余，不应继续把“将来可能恢复”作为叠加模块的理由。原始事件日志有独立审计价值，不能与闲置恢复能力一起直接删掉。

简化方向：清理无消费者的应用接口和候选 checkpoint 支持，或明确归入独立离线审计工具；核对是否存在需要读取的历史数据，再决定保留只读解码能力。数据库迁移历史及原始日志不得未经数据核验直接回滚/截断。

验收：生产入口无闲置恢复依赖，日志仍能按账户审计；旧数据如需读取有明确入口；启动仍执行受支持的恢复协议。

### 7. P2：配置装配层数多、运行函数仍承担大量生命周期

证据：apps/live_rollout/main.py:1164 的 run_command 有 54 个参数；runtime_options.py:56 的 LiveRunOptions 接收后再经 :307 解析 CLI、环境和 manifest；runtime_orchestrator.py:356 接收分组配置，但 run_live_daemon 仍跨 1,542 行，解包参数、创建资源、加载恢复状态、启动任务并装配多个闭包。部分规则常量仍通过私有名称跨模块引用。

不可变分组配置和 manifest 对多账户复用有益。问题是部分选项仍在多个入口解析/传递，运行函数的生命周期知识没有充分集中；仅把函数切成若干转发模块不会解决这一点。

简化方向：生产以 manifest 为主要输入，仅保留必要的身份、配置位置和运行控制参数；明确保留的本地/一次性命令独立装配。配置只解析一次。资源所有权、启动恢复、运行监督各有单一入口，替换现有对应代码，避免再加外层 facade。

验收：相同配置产生相同策略 hash；显式冲突仍拒绝；部分启动失败与取消后资源完全释放；密钥不进入日志和配置摘要。

### 8. P3：Hub 的传输实现可以小范围收敛

行情状态 Hub、最新报价 Hub、账户事件 Hub 各自包含连接、订阅确认、队列、重连与序列化实现。传输层有共同维护机会，但状态回放、最新值合并与账户成交顺序语义不同，不能统一成一种队列或一套丢弃策略。

只提取已证实相同的连接/订阅辅助逻辑，并保留显式业务协议；没有明确重复修改案例前，不设计通用事件总线、插件系统或万能 Hub。优先级低于账户消费及上下文收敛。

## 应保留的设计

- 公共行情的共享采集与广播：多个账户消费同一市场事实，避免每个策略自行采集。market_data/runtime_states.py:367、:915 的持久队列将数据库写入与实时工作分开，属于必要隔离。
- ExecutionBook 的统一状态提交，以及 PositionLedger 的纯确定性归因：前者维护 mutation/事务协调，后者计算批次、数量守恒和零交叉，两者不能仅因都涉及持仓而合并。
- 订单状态机、稳定订单身份、幂等、reservation 与 outbox：网络超时后必须区分未提交与已提交但回执丢失。可以收敛恢复入口，不能删掉这些事实。
- 异步 checkpoint writer：合并周期写入、失败重试和退出 flush 有明确作用；coordinator 管调度、writer 管 I/O 也有清晰职责。可简化 coordinator 的按条数/墙钟 phase/dirty age 多套触发策略，不应把数据库写入放回策略主循环。
- 租约、批准和最终提交时的风险复核：跨进程交易所有权与新增风险检查各有用途；展示层不应重复拥有授权决策。
- Dashboard 查询模块及隔离研究采集：只读查询与不运行策略的研究归档具有独立用途，当前没有证据支持大规模重写。

## 建议顺序与验收原则

先清理明确无人使用的能力；主要业务重构优先处理账户消费中的 REST/多轮重试等待。随后统一运行层状态发布和上下文事实读取，再收敛退出恢复及生产配置入口，最后考虑 Hub 共性和小范围调度简化。

每一步必须减少旧路径、状态副本或调用方需要知道的条件；不以新增文件/Protocol 数量作为完成标准。保持原子事实提交、订单幂等、每持仓顺序、版本冲突保护和资源释放。性能收益需在改造前后测量 SQL 次数、账户事件提交延迟、消费积压和交易所查询数；静态审查不能代替生产验收。

## 实施进展：账户事件消费不再等待持仓同步

已删除账户事件消费者内的八次退避重试（累计 63.75 秒）及对应配置入口。每条事件仍先完成订单身份核验，再提交账户快照，然后只检查一次退出上下文。若持仓仍待同步，消费者立即继续读取下一条事件；后续账户、行情和退出通道负责刷新上下文。没有新增后台重试任务。

待同步持仓继续由上下文发布的 pending-position 开仓门禁保护，不再因消费者重试耗尽被改写为 unmanaged，也不再为这一暂态写入独立的退出失败状态。真实退出失败和订单身份冲突的保护逻辑保留。

本次仅消除消费者内的同步退避等待。订单事件在发布快照前仍可能等待 REST 身份核验，闭合 K 线通道中的待同步重试也仍存在，因此尚不能宣称所有账户消费路径已经摆脱 REST 阻塞。下一步应完善 WS 订单事实表达，再用其满足身份与累计成交校验，避免为了消除等待而破坏成交幂等和持仓归属。

验证：新增连续事件回归场景，第一条持仓待同步时不允许 sleep，第二条账户快照必须先提交再进行下一次决策；相关回归集 1364 项通过。未部署生产。

## 实施进展：完整 WS 订单事实直接驱动现有状态机

账户 Hub 新增可选 order_update，透传 Binance ORDER_TRADE_UPDATE 的完整 o 对象，包括终态订单。旧消息没有该字段仍可解码。正常订单事件按 client_order_id 直接读取一条持久化订单，不再扫描本次运行的全部未决订单，也删除了 load_order 的动态能力探测。

完整事实经过客户端 ID、交易对、方向、订单类型、持仓方向、reduce-only、原始数量、限价和已绑定交易所订单 ID 校验后，调用现有 apply_observed_snapshot；累计成交量、均价及交易时间不完整或无效时才回退 REST 核验。明确的身份冲突继续触发保护，未记入本地日志的订单仍请求恢复。不增加成交量的终态重放、累计数量倒退和同数量的较旧观察不更新订单；撤单终态后迟到的新增成交仍提交事实。账户投影仍在订单事实落库后发布。

WS 的交易时间只有毫秒精度，因此状态机事实 ID 同时包含累计成交量和均价，防止同一毫秒的不同部分成交被去重；完全相同的重放仍只通知一次。沿用现有账户成交记录和 Book 累计水位，没有另建订单状态机或后台任务。

字段依据：[Binance USDⓈ-M 用户数据流文档](https://developers.binance.com/en/docs/products/derivatives-trading-usds-futures/user-data-streams)。

验证覆盖完整新单、部分成交、成交、撤单、过期、身份冲突、缺失/无效字段、终态及乱序重放，另用真实状态机验证同毫秒两次部分成交和重复事件。相关回归集 1394 项通过；本次核心模块类型检查和 Ruff F/I 通过。应用入口已有 RetentionAuthority 类型错误，本次未修改该位置。未部署生产。

限制：事实持久化及执行调度仍需等待；同一执行调度键上的恢复 REST 也可能占用调度器。本次消除的是完整 WS 事件主动发起 REST 核验的路径，尚不代表所有恢复工作均与消费完全隔离。周期未决订单修复及缺失事实的 REST 兜底保留。

## 实施进展：订单事实不再排在 REST 命令后面

apply_observed_snapshot 不再进入持仓命令优先队列，而是直接调用现有事实落库路径，再提交 Book 累计观察。提交、撤单、REST 恢复和缺席证明仍使用原命令队列；没有新增队列或后台任务。协调器关闭后拒绝新的观察，调用方仍负责先停止账户消费者再关闭执行运行时。

后端把快照提交的串行保护放到独立 observation lock 中；所有命令返回的快照和 WS 观察共用这一短提交路径，交易所请求及退避等待不持有它。apply_observed_snapshot 不再取得命令锁，因此后端开启 serialize_commands 时也不会让慢 REST 查询阻塞已有事实的落库。该锁保护保存成交、追加订单事件及本地观察回调，不涵盖网络查询。

验证使用真实状态机和协调器，在同一持仓 REST 查询持续挂起时提交 WS 成交事实，分别覆盖 serialize_commands 开启和关闭，并确认后续相同 REST 响应不重复追加事实；另验证两个事实写入保持串行、关闭后拒绝观察。相关回归集 1398 项通过，修改的两个实现模块类型检查及 Ruff F/I 通过。未部署生产。

剩余限制：不完整 WS 事件仍会在消费者中等待 REST 兜底核验；数据库故障或慢事实提交仍可延迟消费者。命令队列中的慢恢复请求也仍可能延迟同持仓的后续交易命令。这次解开的是完整 WS 事实对命令网络等待的依赖，不宣称所有等待已经消失。

## 实施进展：不完整订单更新交给现有修复任务
