# 对账与就绪状态解耦（2026-10-01）

## 事实与职责

生产四账户均配置轻量 REST 快照等待间隔 15 秒、完整 REST 对账等待间隔 60 秒、已平仓历史品种补查间隔 21600 秒、每批 10 个品种。等待间隔还需加上本轮执行耗时，不能称为严格墙钟周期。

轻量快照只保存余额及持仓观测，既不核验挂单/成交覆盖，也不替换 AccountUserDataState。完整对账会替换实时账户基线，并按排空、冻结、恢复 deferred events 的协议保证一致性。前者没有理由复用后者的账户暂停状态。

## 第一阶段：轻量观测与实时应用

- daemon 的轻量快照仅获取 REST/persistence 串行锁，不获取实时账户状态锁，不停止事件接收，也不修改 reconciliation_active/accept_events。实时事件仍应用到内存并通知执行消费者，此阶段持久化事件仍排队等待 REST 完成（第三阶段已移除网络等待）；原有有界队列及溢出恢复机制继续生效。
- 完整对账的基线替换、成交补齐、事件回放和 SYNCING 保护保持有效。此时尚未应用的事件确实会影响可信账户状态，不能直接把状态改成 READY。
- Dashboard 对 syncing 账户准确报告 account_syncing，其他未就绪情况报告 account_not_ready。ready_readonly 表示观测模块没有交易写权限，并不表示拥有独立批准/租约的策略只能只读，不能将它误报为 account_readonly_mode。

## 验证

新增回归先复现阻塞轻量快照令心跳变成 SYNCING；修复后在 REST 调用尚未结束时，心跳仍 READY_READONLY，真实 ACCOUNT_UPDATE 已应用并通知消费者，持久化仍与 REST 串行且最终包含更新余额。另一回归先复现 Dashboard 把 syncing 误报为 readonly 权限，修复后准确说明原因。完整对账期间事件延迟回放、补成交期间 SYNCING、持久化失败恢复及队列溢出原有测试保持通过。

账户同步、Hub 网络、Dashboard 与策略就绪隔离相关回归共 664 项通过，修改的两个实现模块 mypy 通过，Ruff F/I 与 git diff --check 通过。

## 第二阶段：后台获取与受保护切换

已将完整对账拆为可选后台获取和受保护基线切换。只有已有 READY_READONLY 基线、基线年龄在 0～180 秒内、成交补齐已完成、事件及持久化队列为空、无恢复请求，且 WebSocket 有明确的开放连接标识时，才后台获取 REST 余额、持仓、挂单和成交。获取期间实时事件继续应用并通知消费者；此阶段持久化与 REST 仍通过原有锁串行（第三阶段已拆开）。未知连接能力的旧服务走原保护路径。

切换前排空队列并验证事件接收代数、连接标识、恢复标记及候选快照时效。没有变化时复用候选结果，避免将网络扫描耗时纳入冻结窗口；收到任何事件、断开或重连、队列恢复请求、基线过期时，拒绝候选基线，保留其不可变成交和单调游标后重新进行受保护对账。首次扫描发现的新成交会合并到最终通知，避免扫描缓存导致补成交通知丢失。事实保留接口校验账户范围，数据库写入成功后才推进内存游标，不发布账户快照或进程状态。

后台心跳使用真实基线时间检查时效，不能用心跳时间延长可信期限；连接连续性失效或基线过期会恢复 SYNCING。新增并发回归覆盖扫描期间事件实时应用、无事件直接切换、有事件重新获取、断开、重连、过期，以及成交保留失败和跨账户拒绝。678 项相关测试通过，三个修改的实现模块 mypy、Ruff F/I、git diff --check 通过。

## 第三阶段：事件提交与 REST 网络请求解耦

WS 持久化 worker 和后台对账结果提交不再获取 daemon 的 REST 请求锁。同步模块内部只对已经获取的数据进行提交串行化，锁覆盖时效判断、数据库提交和提交缓存更新，不覆盖交易所网络请求。轻量快照和完整扫描等待 REST 时，WS 事件可以完成落库；单账户的有序事件 worker 与有界队列、溢出恢复机制继续有效。

轻量快照在提交锁内检查真实观测时间：如果扫描期间已有较新的事件或观测，丢弃迟到的轻量快照，不修改余额及持仓缓存。完整扫描不再提前修改余额历史缓存和活跃持仓集合，只有接受并成功提交的结果更新这两项；迟到的完整结果仍仅保留不可变成交和单调游标。由此避免迟到 REST 结果恢复旧缓存、制造重复零余额记录或错误覆盖持仓跟踪。

新增回归在旧代码上分别复现 WS 落库等待 REST、迟到轻量快照写入旧余额、迟到完整扫描恢复旧缓存。修复后验证网络请求未返回时 WS 已完成提交、旧观测不会修改历史或缓存、真正的数据库提交按顺序完成；第二阶段事件并发用例也增加了扫描返回前已落库的断言。681 项相关测试通过，两个修改实现模块 mypy、Ruff F/I 与 git diff --check 通过。

数据库提交慢仍可能积压事件持久化队列，这是存储吞吐约束，不应由 REST 网络耗时放大。本阶段没有增加独立事件日志，也没有移除恢复/基线切换期间暂缓状态应用的旧协议；后续需要将持续接收和有序记录与账户投影修复进一步拆开。

## 后续约束

轻量观测已不暂停实时事件；完整对账在连接连续、基线新鲜且扫描期间没有新事件时，也不再因慢速网络获取而暂停事件应用。启动、恢复、成交补齐和扫描期间状态发生变化的账户仍使用受保护对账，因此 60 秒对账期间仍可能限制入场。下一步若要缩短活跃账户的窗口，需要建立可验证的 REST cut 与期间事件覆盖协议；不能直接回放已经去重的事件或把旧 REST 快照重标为新时间。不能仅延长周期、忽略 SYNCING 或提高事实过期阈值来消除降级。

该修复已合入 main，后续解耦工作直接在 main 继续。尚未发布生产，生产继续运行此前验收版本。
