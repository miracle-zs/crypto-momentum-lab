# 对账与就绪状态解耦（2026-10-01）

## 当前设计

第八阶段已取代第二、第四阶段的周期候选切换流程：正常运行由 WS 维护内存账户状态，周期 REST 只检查差异；有并发事件时暂缓比较，没有证据表明缺口时不重建账户。以下阶段记录保留为演进历史，部署状态以文末为准。

## 事实与职责

生产四账户均配置轻量 REST 快照等待间隔 15 秒、完整 REST 对账等待间隔 60 秒、已平仓历史品种补查间隔 21600 秒、每批 10 个品种。等待间隔还需加上本轮执行耗时，不能称为严格墙钟周期。

轻量快照只保存余额及持仓观测，既不核验挂单/成交覆盖，也不替换 AccountUserDataState。当前只有启动、已知缺口恢复及成交补齐等受保护修复会替换实时账户基线，并保留排空、冻结、恢复 deferred events 的协议；正常周期检查不执行该替换。轻量观测和正常周期检查都不应复用修复时的账户暂停状态。

## 第一阶段：轻量观测与实时应用

- daemon 的轻量快照仅获取 REST/persistence 串行锁，不获取实时账户状态锁，不停止事件接收，也不修改 reconciliation_active/accept_events。实时事件仍应用到内存并通知执行消费者，此阶段持久化事件仍排队等待 REST 完成（第三阶段已移除网络等待）；原有有界队列及溢出恢复机制继续生效。
- 完整对账的基线替换、成交补齐、事件回放和 SYNCING 保护保持有效。此时尚未应用的事件确实会影响可信账户状态，不能直接把状态改成 READY。
- Dashboard 对 syncing 账户准确报告 account_syncing，其他未就绪情况报告 account_not_ready。ready_readonly 表示观测模块没有交易写权限，并不表示拥有独立批准/租约的策略只能只读，不能将它误报为 account_readonly_mode。

## 验证

新增回归先复现阻塞轻量快照令心跳变成 SYNCING；修复后在 REST 调用尚未结束时，心跳仍 READY_READONLY，真实 ACCOUNT_UPDATE 已应用并通知消费者，持久化仍与 REST 串行且最终包含更新余额。另一回归先复现 Dashboard 把 syncing 误报为 readonly 权限，修复后准确说明原因。完整对账期间事件延迟回放、补成交期间 SYNCING、持久化失败恢复及队列溢出原有测试保持通过。

账户同步、Hub 网络、Dashboard 与策略就绪隔离相关回归共 664 项通过，修改的两个实现模块 mypy 通过，Ruff F/I 与 git diff --check 通过。

## 第二阶段：后台获取与受保护切换

已将完整对账拆为可选后台获取和受保护基线切换。只有已有 READY_READONLY 基线、基线年龄在 0～180 秒内、成交补齐已完成、事件及持久化队列为空、无恢复请求，且 WebSocket 有明确的开放连接标识时，才后台获取 REST 余额、持仓、挂单和成交。获取期间实时事件继续应用并通知消费者；此阶段持久化与 REST 仍通过原有锁串行（第三阶段已拆开）。未知连接能力的旧服务走原保护路径。

切换前排空队列并验证事件接收代数、连接标识、恢复标记及候选快照时效。没有变化时复用候选结果，避免将网络扫描耗时纳入冻结窗口；收到任何事件、断开或重连、队列恢复请求、基线过期时，拒绝候选基线，保留其不可变成交和单调游标后重新进行受保护对账。首次扫描发现的新成交会合并到最终通知，避免扫描缓存导致补成交通知丢失。事实保留接口校验账户范围，数据库写入成功后才推进内存游标，不发布账户快照或进程状态。

后台心跳使用真实基线时间检查时效，不能用心跳时间延长可信期限；连接连续性失效或基线过期会恢复 SYNCING。新增并发回归覆盖扫描期间事件实时应用、无事件直接切换、有事件重新获取、断开、重连、过期，以及成交保留失败和跨账户拒绝。678 项相关测试通过，三个修改的实现模块 mypy、Ruff F/I、git diff --check 通过。

## 第三阶段：事件提交与 REST 网络请求解耦

WS 持久化 worker 和后台对账结果提交不再获取 daemon 的 REST 请求锁。同步模块内部只对已经获取的数据进行提交串行化，锁覆盖时效判断、数据库提交和提交缓存更新，不覆盖交易所网络请求。轻量快照和完整扫描等待 REST 时，WS 事件可以完成落库；单账户的有序事件 worker 与有界队列、溢出恢复机制继续有效。

轻量快照在提交锁内检查真实观测时间：如果扫描期间已有较新的事件或观测，丢弃迟到的轻量快照，不修改余额及持仓缓存。完整扫描不再提前修改余额历史缓存和活跃持仓集合，只有接受并成功提交的结果更新这两项；迟到的完整结果仍仅保留不可变成交和单调游标。由此避免迟到 REST 结果恢复旧缓存、制造重复零余额记录或错误覆盖持仓跟踪。

新增回归在旧代码上分别复现 WS 落库等待 REST、迟到轻量快照写入旧余额、迟到完整扫描恢复旧缓存。修复后验证网络请求未返回时 WS 已完成提交、旧观测不会修改历史或缓存、真正的数据库提交按顺序完成；第二阶段事件并发用例也增加了扫描返回前已落库的断言。681 项相关测试通过，两个修改实现模块 mypy、Ruff F/I 与 git diff --check 通过。

数据库提交慢仍可能积压事件持久化队列，这是存储吞吐约束，不应由 REST 网络耗时放大。本阶段没有增加独立事件日志，也没有移除恢复/基线切换期间暂缓状态应用的旧协议；后续需要将持续接收和有序记录与账户投影修复进一步拆开。

## 第四阶段：统一后台基线切换证据

新增 BaselineRepairAttempt 作为不可变的扫描证据，统一持有扫描开始时的本地事件接收代数、开放连接标识及已验证基线时间。daemon 不再分别维护扫描基线时间和连接标识，也不再向切换方法分别传递事件代数和连接标识；心跳和切换通过同一个证据对象判断连续性及时间有效性，时效函数只保留一份。这一步收敛已有规则，没有增加新的正常/恢复分支。

协议明确区分两种许可：扫描期间允许继续应用 WS 事件，并不代表允许用 REST 候选替换基线。候选切换必须在排空队列、持有账户投影锁后验证连接标识未变、事件代数未变、无恢复请求、候选时间有效。验证失败仅保留成交和游标，并使用原受保护流程重新建立基线。无快照的失败/暂停结果在连续性成立时仍正常传播，不因缺少快照被错误当成正常基线或忽略。

本地事件代数只能证明扫描期间没有收到新事件，不能证明交易所提供了跨 REST/WS 的统一切面。尚未实现独立持久事件日志及跨切面的覆盖验证，也未删除冻结、排空和 deferred events 回放。要替换它们，需要可验证的账户事件顺序与修复切面，不能将本地收到事件的时间伪装成交易所的全局顺序。本阶段不宣称完整基线修复协议已完成。

相关回归 690 项通过，新增协议模块和 daemon 的 mypy、Ruff F/I 与 git diff --check 通过。新增用例区分“WS 可继续更新、候选不能切换”，以及断线、重连、恢复请求、时效边界和无快照暂停结果。所有阶段尚未部署生产。

## 第五阶段：独立原始 WS 事件日志

新增 account_user_data_journal，按 environment/account_label 隔离，记录解析后的原始 WS 载荷、事件身份、交易所时间及可用更新编号、本地接收时间、接收进程会话和连接标识。事件进入状态应用、暂缓、恢复或跳过分支之前先提交原始日志；此写入不获取 REST 请求锁、账户投影锁或观测提交锁。修复期间暂缓状态应用的事件也会记录，不能只保存应用后的账户快照。

日志由数据库分配递增序号，同账户事务锁保证序号分配与提交顺序一致。重复 event_id 在同一环境和账户内返回首次记录的序号，保留首次接收信息；不同账户、不同环境可以分别保存同一事件。提供有界、按账户过滤的 after_sequence 分页读取，重建 repository 后仍能读取。序号可以存在空洞；它表示本地日志的提交顺序，不代表交易所全局顺序，也不能证明 WS 断线期间没有漏事件。新进程会话标识使进程重启后重复的连接计数可区分。

原始日志提交失败会触发账户恢复，停止应用未记录事件。原有 WS reader/dispatcher 分离机制继续使用有界队列；数据库长时间不可用仍可能积压或触发溢出恢复，不能承诺无限缓存。旧同步适配器没有记录能力时保留兼容行为；生产 ExecutionAccountSyncService/PostgresAccountRepository 已接入必经日志路径。

这一阶段建立了修复的持久输入，但尚未将投影恢复改为“已验证基线 + 持久事件游标”，也未删除 deferred events 和冻结分支。后续 checkpoint 必须绑定基线与日志游标、识别断线/写入失败缺口，再依据可验证的字段覆盖恢复；不能直接回放已在 REST 基线中包含的成交。日志暂不自动删除，保留策略需与消费者 checkpoint 绑定，不能先按时间截断仍可能需要的事件。

验证：三个 daemon 新用例在旧代码上失败，修复后通过，覆盖普通应用、修复期间记录和日志失败保护；实际同步模块测试确认日志提交不等待投影提交锁且不修改账户观测缓存。707 项相关单测/回归通过，服务器临时隔离 PostgreSQL 16 容器的 10 项仓储集成测试通过，并验证从空库升级、0046 回滚及重新升级。临时容器与 SSH 转发已清理，生产容器继续运行原验收版本。六个修改实现模块 mypy、Ruff F/I、git diff --check 通过。新增迁移尚未应用到生产数据库，代码尚未部署生产。

## 第六阶段：完整基线与日志前缀的持久绑定

复用 account_reconciliation_runs.details 保存 schema_version=1 的 baseline_checkpoint，包含对账身份、完整 AccountSnapshot、同账户日志游标、接收进程会话及连接标识；不新增 checkpoint 表。完整基线包含历史稀疏存储可能省略的零余额和零持仓，因此不能仅用历史行拼装恢复基线。checkpoint 与对应账户快照、成交和对账记录共用原有事务，数据库失败时一起回滚。

只有连续连接且无并发事件的后台候选能够携带日志前缀：获取 REST 前读同账户的已提交日志游标，原有 BaselineRepairAttempt 在切换时验证事件代数、连接、恢复标记及时效。候选被拒绝后重新获取的结果不继承候选 checkpoint；成交补齐或未就绪结果也不得保存 checkpoint。服务验证 checkpoint 与完整基线、账户范围和对账身份一致，仓储在同一事务内检查游标锚点确实属于该账户。序号零表示空日志前缀，不能将其他账户的全局数据库序号当成本账户进度。

同时修复第五阶段引入的异步切面漏洞：原始日志尚在提交时，事件队列可能仍为空；此前后台扫描可能把已收到但未提交、未应用的事件计入起始代数，随后错误地认为没有新事件。新增回归在旧实现上复现错误 READY_READONLY；现在记录在途日志提交，只在不存在该未完成阶段时允许后台切面。日志提交仍独立于 REST 请求与状态应用锁。

仓储提供按账户读取最近持久 checkpoint 的入口，校验版本、字段类型、基线身份、账户和时间，之后可用 journal_sequence 分页读取日志尾部。该读取能力用于验证重建 repository 后的基线/日志关系；当前 daemon 启动仍进行原有 REST 建基线，没有接入自动恢复，也没有把“日志序号大于游标”等同于“可以直接安全回放”。跨接收进程或连接重建、日志失败缺口、期间成交是否已包含于 REST 基线仍需独立证明。旧冻结和 deferred events 回放分支继续保留。checkpoint 复用现有对账记录的保留规则，后续事件日志裁剪需与基线保留及消费者游标一起设计。

验证：710 项相关单测/回归通过；真实隔离 PostgreSQL 的两项日志/checkpoint 集成测试通过，覆盖完整快照读回、重建 repository 后读取未覆盖尾部、跨账户游标拒绝，以及数据库失败后的整体回滚。六个修改实现模块 mypy、Ruff F/I、git diff --check 通过。服务器临时测试容器和转发已清理，代码及前一阶段 0046 迁移仍未发布生产。

## 第七阶段：按实体拦截已被 REST 更新超越的旧账户事件

AccountUserDataState 在初始化及 replace_snapshot 时保存每个资产、每个 symbol/positionSide 的 REST raw_payload.updateTime。ACCOUNT_UPDATE 应用时按行比较明确的原始 T：仅当 T 严格小于对应实体更新时间时跳过该行；同一事件中时间较新的其他实体继续应用。因此修复后 deferred 回放和普通延迟接收均不能通过这种已知旧行将 REST 余额、持仓恢复成旧值。全部行被跳过时 changed=False，不再制造重复观测提交；原有事件身份和更新序号 bookkeeping 仍执行。基线时间独立于后续 WS 行载荷保留，每次基线替换重新建立，不从本地接收时间推断。

字段依据：[Binance USDⓈ-M 余额接口](https://developers.binance.com/en/docs/catalog/core-trading-derivatives-trading-usd-s-m-futures/api/rest-api/account)说明资产 updateTime 为最后更新时间；[持仓接口](https://developers.binance.com/en/docs/catalog/core-trading-derivatives-trading-usd-s-m-futures/api/rest-api/trade)提供持仓 updateTime；[用户数据流](https://developers.binance.com/en/docs/products/derivatives-trading-usds-futures/user-data-streams)区分交易时间 T 和生成时间 E。本实现由这些字段推导逐实体旧绝对值不应覆盖较新基线的规则，不将其宣称为交易所统一序号或原子快照保证。

边界：正整数以外的时间、零更新时间、缺少 T、同毫秒事件仍沿用已有应用及恢复流程，不新增无证据的去重判断；E 的解析回退不能证明 REST 覆盖。此阶段并未解决这些模糊切面，也未改变订单/成交处理，不能凭开放订单缺席推断终态、跳过成交或推进持久消费 checkpoint。因此日志自动恢复、冻结和 deferred 删除仍未完成，当前规则只是收敛其中明确可判定的旧账户行。

验证：新增 14 项回归，覆盖初始化/替换基线、余额与持仓各自新旧组合、事件重复、不可信时间和 E 回退。旧实现明确复现余额 100 被延迟 WS 覆盖成 90；724 项相关回归通过，两个实现模块 mypy、Ruff F/I、git diff --check 通过。没有修改数据库结构，也没有发布生产。

## 第八阶段：周期检查与账户修复分开

正常周期调用 _check_periodic，持续由 WS 维护 AccountUserDataState。REST 网络扫描不持有投影锁，也不设置 reconciliation_active/accept_events，不排空队列、不替换内存状态。检查时有在途日志、排队事件或扫描期间接收代数变化，结果只保留真实成交及单调游标，留到下一轮比较，不再冻结后重新扫描。连接变化、明确账户差异、返回未就绪或成交补齐未完成，才请求原有独立恢复入口；首次启动及不支持检查能力的旧适配器仍使用原修复路径。

比较只看账户事实：模式/配置、钱包余额、非零持仓数量/入场价/保证金类型/杠杆，以及挂单内容。忽略随行情变化的 mark price、未实现盈亏、notional 和 WS 未维护的 REST available balance；REST 枚举的额外零资产/零持仓不构成差异。忽略估值变化不等于证明全部账户字段一致，可用余额和估值的轻量 REST 观测职责仍保留。

可比较且事实一致时，不调用 replace_snapshot；对消费者发布当前 WS 投影和本次真实成交覆盖材料，后台保存这次已匹配的 REST 审计观测，保留现有持久对账 head 与覆盖证明的进度。扫描期间发生 WS 更新时，不发布审计全量快照，也不保存候选账户观测。后台写入继续复用观测时效保护，不能覆盖晚于候选的 WS 持久状态。真实成交身份在事实提交失败前仍通知消费者；已知恢复期间的成交通知携带 SYNCING，不能通过补成交通知重新宣称 READY。

删除 BaselineRepairAttempt 模块、候选切换参数、后台扫描 180 秒基线门槛、候选失效后再次扫描及新成交跨两次扫描合并分支。第六阶段的 checkpoint 存储格式和读取能力保留，daemon 不再通过周期候选生成新 checkpoint，也没有启动自动日志恢复。冻结和 deferred 回放只保留在实际修复中，不能把正常检查的删除误报为全部恢复协议完成。

fetch-only REST 失败只抛出错误，供日志和重试处理，不再由同步模块写 DEGRADED；原 sync_once 的失败发布语义保持不变。WS 日志失败、队列溢出、已知断线及配置不符合要求的保护仍有效。持续活跃期间检查可能一直无法比较，这是当前限制；不能把未比较标记为已验证，也不能仅凭 WS 连接开放证明没有静默丢失事件。
