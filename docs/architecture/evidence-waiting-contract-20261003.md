# 对账结果契约：等待证据与真实冲突

## 已确认的问题

跨 epoch 的账户快照缺少来源锚定成交扫描，原来与同身份不同载荷等真实矛盾一样
返回 `EvidenceConflict`。这并不说明账本已被证明错误，而是尚不能建立新旧来源的
连续性。Coordinator 将这类结果按错误聚合，每次快照重复输出。

最小回归命令：

```bash
rtk proxy .venv/bin/python -m pytest -q tests/unit/execution/test_evidence_waiting.py
```

修复前：非零等量、非零不同量、带持久化历史的零仓位三种缺证据场景被误报为
冲突；连续三次快照记录三条冲突错误。四项复现断言失败。

## 结果与边界

`ExecutionObserveResult` 现在包含四种不可变结果：

| 结果 | 含义 | 调用方行为 |
| --- | --- | --- |
| `Applied` | 已应用观察事实 | 使用已提交投影，仍遵守既有交易就绪与结算门槛 |
| `Duplicate` | 事实身份已接受 | 不重复应用事实 |
| `WaitingForEvidence` | 尚缺完整来源证明或父检查点 | 保留旧投影，不确认新 epoch、不当作成功 |
| `EvidenceConflict` | 身份、序列、检查点绑定、持久化事实等存在矛盾 | 保留拦截及错误报告 |

等待原因使用 `EvidencePendingReason`，不通过错误文字推断：

- `stream_recovery_proof_required`：跨流恢复缺少扫描或分页尚未完成。
- `parent_checkpoint_unavailable`：来源扫描所引用的父检查点当前不可用。

只有实际缺少来源证明的分支改为等待。完整但不可信的扫描、父检查点 ID
不匹配、持久化身份冲突、倒退序列及其他严格校验继续拒绝，不统一降级。
不同数量的两个跨 epoch 快照，也必须先取得完整来源证明才能判定数量矛盾。

## 状态所有权与事务保证

ExecutionBook 决定事实是否应用。缺证据时不改变旧持仓数量、批次、投影版本或
持久化 head，新 epoch 的仓位读取仍被阻止。组合成交中出现等待结果时，当前
事务整体回滚，不能提交此前已暂存的部分成交。等待不会将持久化子系统标为失败。

Coordinator 负责等待状态的日志去重，按 PositionKey、目标 stream/epoch 与
原因记录状态。相同等待只输出一次 INFO；事实被应用或确认为重复后清除等待，
输出一次 `account_snapshot_execution_book_evidence_ready`。该日志表示这一缺证据
等待已解除，不表示所有命令已经结算或该仓位必然可交易。真实冲突仍输出 ERROR。

已确认零仓位缓存只接受 `Applied` 或 `Duplicate`，不再用“不是冲突”作为成功
条件。订单累计事实如果返回等待，抛出明确的执行就绪错误，沿用 UNKNOWN 保护
与异常传播，不能向上层假报成功。连接和事务失败仍自然暴露。

没有增加 REST 对账频率或后台轮询，没有增加数据库表和持久化订单状态。
等待依赖现有账户恢复扫描和新事实继续推进，调度收敛参见
[第一步记录](recovery-scheduling-convergence-20261003.md)。

## 验证

新增 15 项回归：等待保持旧账本与读取门槛、等待日志去重、组合成交停止与回滚、
等待解除后可再次报告、真实冲突日志保留、父检查点缺失与错绑的区分、订单累计
结果不能把等待当成功，以及完整扫描数量矛盾与不完整扫描的区别。

全量单元测试 **3212 项通过**，保留既有 Starlette 弃用及异步生成器关闭两项
警告。Ruff 与差异空白检查通过，已有长行文件的 Ruff 检查忽略 E501。
结果契约、组合观察与 Coordinator 三个文件通过 Mypy；ExecutionBook 的 6 个
类型问题与 HEAD 基线一致，本轮未修复这些既有问题。

真实 PostgreSQL epoch 接续集成验收使用独立临时 `cml_test` 数据库，经 SSH
回环转发连接，限制 0.5 CPU、256 MiB 内存，完成空库全迁移后执行。验收结果
为 **30 项通过，耗时 259.53 秒**，覆盖跨 epoch 接续、错误来源证明、持久化
重放、检查点完整性与原子恢复。测试完成后已删除临时容器并撤销 SSH 转发。
生产交易数据库不参与测试；本次变更尚未提交或部署。

本轮只完成观察结果契约与日志处理。按任务种类、仓位分别唤醒恢复，以及退出

该结果契约的修复范围。
