# 正常使用优先的简化复查（2026-10-01）

## 结论与范围

系统存在职责分散、兼容分支过多和重复状态处理的问题。前十四步主要解除阻塞、修复一致性，并没有让整体结构足够简单。继续按异常场景不断增加协调层，会背离本次要求。

本次沿行情接收→上下文→策略→风控→持久化→下单，以及账户事件→订单事实→持仓→退出的本地调用链复查。覆盖 live_rollout 主路径，并检查 execution_account 与 market_data 接口；不是全仓逐行审计，也没有连接服务器。当前 live_rollout 为 85 个 Python 文件、28097 行，execution_account 为 41 个文件、13148 行，market_data 为 24 个文件、8308 行。统计包含注释、空行和接口；不能仅凭行数判定过度设计。daemon 构造需了解 25 个输入，exit_processor 13 个，scheduled_controller 14 个，反映调用者需要掌握较多接线知识。

## 正常使用应先通过什么

1. 公共行情 WS 和账户 WS 持续接收；策略、REST、日志写入慢时不阻断接收。
2. 有效行情进入策略；预热完成后，只在账户事实有效、风控允许时开仓。
3. 一次信号最多产生一次交易效果；下单确认后，WS 成交更新订单和持仓。
4. 正常持仓能按报价、收盘或持仓期限退出；退出数量正确，不反向开仓。
5. 启动时恢复必要的持仓/未决订单；普通断线能重连；未知下单结果先查清再决定。

不把“所有罕见故障组合都能自动恢复”作为本轮正常使用的前置条件。测试通过不等于交易所和生产实盘验收；仍需后续一次实际部署观察上述闭环。

## 主要发现与删减顺序

### 1. 先删除热路径上的多签名兼容

证据：entry_lane.py 的 _current_readiness 先按 keyword 调用，遇到 TypeError 再按 positional 调用，再遇到 TypeError 改成无参数。生产 runtime_orchestrator.py 接入的是接受 symbol 的 lambda，而配置声明仍是 Callable[..., ExecutionReadiness]。

问题不只是代码多：真实 provider 内部抛 TypeError 也会触发再次调用，容易掩盖错误。context.py 同时发现 is_current/is_context_current、invalidate/invalidate_cache；postgres_runtime.py 又实现接口别名。已统一失效入口，但接口兼容仍未完全删除。

动作：逐个确认实际调用方，统一一个明确签名；旧签名在接线处一次性处理，确实无人使用才删。不要在每次策略评估时猜方法形状。先做这一项，行为范围最小，不需要新增模块。

### 2. 退出职责应收敛，不能继续拆转发层

证据：exit_channels.py 管三个循环与退避；daemon.py 转发；exit_event_coordinator.py 加载事实并选入口；exit_lane.py 管两类工作与汇总；exit_processor.py 同时拥有规则调用、交易对锁、未知回执、候选生成与订单提交；exits.py 实现退出业务规则。渠道职责与处理职责有必要区分，但调用方要同时理解多层状态、回调和结果分类。

quote 与 grace 各保存 retry_at/retry_delay，重复维护退避及故障回调；exit lane、entry control、运行 readiness 又分别汇总退出故障。这些不是已证明可以全部删除的“同一个状态”，但足以要求先明确单一写入归属。

动作：保留原接收任务和不会阻塞接收的工作处理；优先合并重复的结果分类/退避，并减少纯转发入口。业务退出规则保留一个实现，提交保留一个入口。合并后删除旧类/旧接线，而不是再加一个统一协调器。不能为了少文件把慢下单重新塞回 WS 接收。

### 3. 恢复状态有两个不同事实层，先分清再删

证据：decision_facts.py recover_pending_exits 处理 durable decision/outbox；exit_processor.py recover_requested_exits 处理 UNKNOWN exchange receipt，后者另存运行期请求映射、预算与退避；order_reconciliation.py 驱动二者。

前者表示“退出决定已记录，效果是否释放”，后者表示“订单请求发出后交易所结果是否已知”。因此不能仅凭两个 recover 名称就删掉其中一个。正常确认路径应直接完成，只有未决结果进入修复。

动作：先核对当前正常订单经过哪些状态，列出每份状态来自哪个 durable fact。优先去掉可从持久化身份推导的重复内存状态；重启恢复以原持久化订单/意图为依据。撤单回退完整性确实待验收，但不因此引入通用恢复协议、更多状态机或并行修复框架。

### 4. 状态显示应派生，不能反过来成为第二套风控

证据：entry_control.py 保存多个入口门槛和退出故障，readiness.py 计算 TradeabilitySnapshot，runtime_orchestrator.py 汇集健康/事实；实际提交还经过 submission_fence.py 的租约与事实校验。

最终提交检查有现实意义：评估到 POST 之间控制状态可能改变，不能把它当重复判断直接删。对账进行中、未预热、未管理持仓、真实退出失败也不是同一种异常。

动作：操作门禁保持明确来源，面板状态从这些来源派生。避免周期任务仅因“正在运行”就写入新的冻结状态；本轮未认定当前生产有这种错误。合并前先核对原因来源，不再增加状态枚举来解释已有状态。

### 5. 观测代码可以瘦身，但没有证据证明所有 await 都会阻塞数据库

证据：telemetry.py 为 1618 行，维护 phase trace、来源索引、订单索引、事件队列和衍生时延；_record_phase 最终使用 put_nowait，_write_events 后台批量写入。runtime_orchestrator.py 已配置持久化事件过滤。

动作：列出生产实际查询的事件和字段，保留启动状态、交易提交/成交/失败与必要时延；有明确消费者的字段保留。无人消费的衍生诊断再删，不再增加通用 trace 模型。暂不能按行数删掉全部 telemetry，也不能把已有后台持久化当作同步数据库等待。

### 6. 小型转发模块与配置有清理空间，优先级靠后

exit_control.py 主要封装一个 enabled 布尔值和日志；entry_policy 的 legacy/compare/enforce 路径及两项开关增加正常开仓路径分支。它们是候选删减项，但不能假设两个账户配置都只使用一种模式。

动作：先确认仓库配置和实际部署使用方式，再删除无使用的模式或合并浅模块。不要为了少一个文件反而增加 daemon 接线，也不为每个纯函数再定义一个 Protocol。

## 必须保留的最小机制

- WS 接收与慢处理分离，队列有界；公共行情共享、账户私有事实隔离。
- 风控数量/限额、reduce-only 或 hedge scope、持久化订单身份与幂等提交。
- 真正持仓归属不清时限制开仓；最终租约/fencing 检查。
- 必要持久化成交与持仓事实；启动基线、普通断线重连、未知结果 REST 查询。

这些服务于真实交易闭环。删除它们可能只是把正常使用中的不确定性转成重复订单或错误仓位。

## 后续执行约束

先固定正常闭环行为，再按“签名兼容→退出重复处理→冗余状态→无消费者观测”顺序删减。每项说明删掉哪个旧入口/状态、正常使用由哪个现有入口负责，相关业务测试通过就结束；不以新增类、接口或更多测试数量作为成果。不重写整个系统，不先引入统一协调器、插件架构或新恢复状态机。

前一计划中“补齐跨进程恢复意图”暂移到真实订单持久化事实核对之后；不继续把假设故障逐个扩展为实现任务。当前累积改动尚未提交或部署，本次只增加复查报告与计划约束，不改生产逻辑。

## 策略保持不变后的剩余删减复查

用户本次要求先不调整策略差异，只检查过度设计与冗余。以下是当前工作树的静态调用核对结果，本次未执行代码删除，也未部署。

### 可直接清理

1. 删除 `live_rollout/entry_policy_compare.py`。该文件只有 domain 模块的兼容导出，无实现；仓库内只有 `tests/unit/live_rollout/test_entry_policy_compare.py` 引用它，生产直接使用 domain 实现。测试改为直接导入 domain，保留已有策略比较行为用例；文件归位不需要重写测试。
2. 删除 `gates.py::_order_state_is_uncertain`。它只是转调公开函数 `order_state_is_uncertain` 的私有兼容别名；仓库搜索没有调用方。公开判断及其风控行为保留。
3. 删除 `exit_processor.py::_load_fresh_exit_context` 中对 `pending_position_symbols`、`unmanaged_position_symbols` 的 `getattr(..., ())` 兼容默认。provider 返回明确的 `LiveDaemonRuntimeContext`，两个字段已在该类型定义；改成直接访问，测试替身遵守同一类型约定。不能把缺少持仓事实字段当成空集合。

### 下一批收敛，不能直接整层删除

4. 收敛退出上下文的持仓阻塞原因检查。`exit_event_coordinator.py::_load_context` 与 `exit_processor.py::_load_fresh_exit_context` 重复检查 pending/unmanaged symbol 并拼接原因；放在已有 context 模块中的一个小函数即可，不新增协调器或状态类。两处加载的触发时机、异常处理及提交前 currentness 复核不同，仍需保留。
5. 退出协调器的四处失败日志判断重复。可以在现有类内部收敛共同的“真实失败才记录”判断，保留各触发源的事件名、symbol 和返回值。收益较小，排在兼容项之后；不要引入通用事件分发框架。

### 当前没有足够依据删除

- `legacy / compare / enforce` 开仓模式：生产四账户使用 enforce，但命令行、纸交易、回放仍有真实引用。退役实盘兼容模式需单独界定产品范围；不能将整个 domain 比较实现认作死代码。
- `context_prefetch.py`：当前 daemon/market loop 实际使用，承担有界预取、顺序及取消回收，不能仅凭类和任务多就删除。
- `LegacyOrderIdentityAdapter`：仍承担真实订单/成交事实投影及缺少明细时的恢复；不能依据 Legacy 名称认定无用。
- `exit_event_ports.py`：接口重复列举实际方法，存在简化空间，但删除接口并不自动减少运行复杂度；保留必要依赖隔离，不将删 Protocol 数量当成果。
