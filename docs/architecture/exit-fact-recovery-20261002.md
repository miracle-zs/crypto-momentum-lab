# 平仓事实链路修复与验收（2026-10-02）

## 生产证据

只读查询确认 account-3 / account-4 的账户成交表存在龙虾USDT 入场 BUY 970，订单分别为 1443853511 / 1443852844；执行事实日志没有这两笔 BUY，却收到了后续 SELL。账户空仓不能证明历史事实已修复，更不能把人工平仓归因于自动退出。

策略日志明确记录了 `live_scheduled_flatten_unmanaged_position_not_in_book`、`repair projection does not match actual account exposure` 和反复出现的 `repair context advanced during fact load`。这些是事实投影及修复阻塞，不是“交易所长期查不到开仓订单”的证据。

account-2 曾出现账户级 `Execution reservation settlement requires recovery`。历史日志缺少原始触发命令的完整诊断，不能把后来被拦截的退出命令当作触发命令。新增 Coordinator 日志输出 Book 返回的真实 diagnostics，以便明确定位命令；保留结算保护。

## 修复

1. 账户事件在订单对账或账本发布阶段短暂失败时，保留同一事件并有界重试；失败耗尽后暴露异常，不推进至后续事件。请求恢复同时使上下文失效。
2. 遥测写入移至账户事实发布之后，避免遥测故障跳过真实成交。
3. WebSocket 健康时原来没有周期性 REST 成交重扫。增加默认 300 秒的定时重扫，复用正常串行化对账、来源锚点、完整分页证明和快照发布。实际扫描使用只读交易所接口；不发单、不伪造成交。
4. 修复事务检查最新有效上下文的持仓数量、入场价、事实流和观察时间。内容相同的刷新不再使事务失效；曝光或事实流变化仍中止修复。正常事务锁、版本冲突和提交后 Book 重载检查保留。
5. 修复查询只补充已验证 checkpoint 之后的成交，避免将 checkpoint 以前已折叠成交再次累加。普通轮询游标和本地已存成交不能延长已验证覆盖区间。

## 验收边界

真实独立 PostgreSQL 上验证：仅快照不能恢复缺失入场成交；有明确零仓锚点和完整扫描时能恢复 970；重复重放及重启后仍为 970。已有跨 epoch、截断扫描、哈希冲突及订单终态/真实成交乱序测试继续保留。

周期扫描单测验证健康 WebSocket 下仍再次执行包含成交的对账，并发布结果。修复并发测试验证相同内容刷新允许提交，数量、入场价、事实流变化禁止提交。

上述工程验证不等于真实自动平仓成交验收。生产历史 BUY 是否完整进入日志、原 account-2 阻塞命令是否由真实成交解除，以及新版本是否已运行，必须分别以在线日志和数据库证据确认。未通过真实下单进行测试，也未直接清空生产保护标志。

周期扫描会增加只读 REST 和数据库负载；其频率为五分钟，复用分页截断和恢复失败时的关闭准入行为。完整扫描可能耗时，期间心跳继续运行、事件按现有管道暂存和重放。
